摘要

摘要
LoongArch 是我国自主研发的新型指令集架构，在具备可控性的同时拥有良
好的性能，然而其在推广过程中仍面临软件生态薄弱、主流应用支持不足等问题。
针对上述挑战，本文提出并实现了在龙架构上运行的安卓运行时 ARTOL（Andoird
Runtime On LoongArch），旨在通过支持 Android 应用运行，推动 LoongArch 架构
的生态构建。
本文在谷歌用于运行安卓应用的平台安卓运行时的基础上，设计并实现了适
配于龙架构上运行的系统 ARTOL，该系统面向国产自主指令集 LoongArch 实现了
对 ART 核心模块的全面移植与适配，包括解释器、JIT 编译器以及运行时等关键
子系统。通过 ARTOL 的支持，广大基于 Android 的移动应用程序无需重新编写或
重新编译，便可在 LoongArch 平台上实现透明、无缝地运行，显著提升了该架构
在主流应用生态中的兼容性与实用性，为推动 LoongArch 在移动终端、嵌入式设
备等场景中的广泛部署奠定了坚实的技术基础。
本文主要贡献如下：
1. 实现了在龙架构上运行的安卓运行时 ARTOL。基于原有的安卓运行时，在
龙架构平台上完成了解释器、JIT 编译器及运行时环境的整体实现。实现了
包括基于 C++ 的通用解释器、基于汇编语言的 Nterp 快速解释器，以及包含
汇编器、反汇编器、链接器与指令生成器在内的 JIT 编译子系统，并为不同
执行方式搭建了不同的调试框架。最终构建了从字节码到机器码的完整执行
链路，确保了安卓应用在 LoongArch 平台上的正常运行。
2. 实现了面向运行时子模块的多项性能优化。针对 ARTOL 的关键性能瓶颈，
提出了多项系统级优化策略：包括引入专用的 JNI 编译器，对 @FastNative
和 @CriticalNative 方法进行特化编译，显著降低 JNI 调用开销；实现函数调
用路径的内联优化，有效减少高频函数调用的调度成本；引入 OSR 机制，支
持循环热点从解释到编译的动态替换，提高循环密集型程序的执行效率。
3. 进行了系统性的正确性验证与性能评估。通过功能性测试全面验证 ARTOL
的语义一致性与稳定性；借助 CaffeineMark 等标准基准测试工具，对系统性
能进行定量评估。结果表明，优化后的 ARTOL 在多个关键指标上均取得显
著性能提升，验证了所提出优化方案的有效性和工程实用价值。
关键词：安卓运行时；龙架构；虚拟机技术

ABSTRACT

ABSTRACT
LoongArch is a new instruction set architecture (ISA) independently developed in
China. It offers strong controllability along with competitive performance. However,
during its promotion and adoption, LoongArch still faces challenges such as a weak software ecosystem and limited support for mainstream applications. To address these issues,
this paper proposes and implements ARTOL (Android Runtime On LoongArch), an Android runtime system designed to run on the LoongArch platform. The goal is to support
Android application execution and thereby promote the ecological development of the
LoongArch architecture.
Building upon Google’s Android Runtime (ART), which serves as the core platform for running Android applications, this work designs and implements ARTOL, a
fully adapted runtime system tailored for the LoongArch ISA. ARTOL provides comprehensive support for essential ART components, including the interpreter, JIT compiler,
and runtime environment. With the support of ARTOL, a wide range of Android-based
mobile applications can run transparently and seamlessly on the LoongArch platform
without requiring source code modiﬁcation or recompilation. This signiﬁcantly enhances
LoongArch’s compatibility and practicality within the Android application ecosystem and
lays a solid technical foundation for its adoption in mobile devices, embedded systems,
and other application domains.
The main contributions of this paper are as follows:
1. Implemented the Android Runtime on the LoongArch architecture. Based on the
original Android Runtime (ART), a complete implementation of the interpreter,
JIT compiler, and runtime environment was accomplished for the LoongArch platform. This includes a general interpreter written in C++, a high-performance Nterp
interpreter implemented in assembly language, and a JIT compilation subsystem
comprising an assembler, disassembler, linker, and instruction generator, at the
same time, different debugging frameworks were built for each execution mode
to accommodate their speciﬁc characteristics. Finally, these components form a
complete execution pipeline from bytecode to machine code, ensuring the correct
execution of Android applications on the LoongArch architecture.
2. Introduced multiple performance optimizations for runtime submodules. To address the key performance bottlenecks of ARTOL, several system-level optimization strategies were proposed and implemented: a dedicated JNI compiler was iniv

研究背景与意义
敏捷芯片开发、异构计算架构、先进工艺制程等技术的出现，大大加快了计算

机体系结构的发展。随着技术的发展，因特尔和微软组成的 Wintel 联盟也在 ArmAndroid 所组成的 AA 体系挑战下逐步失去它们所占有的市场。近些年兴起的各种
微架构更是不断冲击着老牌芯片厂商霸主的地位。在计算机体系微架构的不断更
新迭代下，指令集的发展也没有停下它的步伐。而对于一个新兴的指令集来说，要
在久经考验的 X86 和 Arm 架构中立足，除了良好的指令集设计和卓越的微架构
外，完善的软件生态同样不可或缺。

基于 LoongArch 开发的首款处理器 3A5000 同频性能提升超过 20%。以最新一代
微架构 LA664 为基础的 3A6000, 更是在 3A5000 的基础上单核性能提升 60%，多

等国外技术体系在处理器生态领域的长期垄断，更标志着我国在计算机核心领域
实现了从指令集架构、微结构设计、IP 核研发到 ABI（Application Binary Interface）

够发挥最大的软件性能，获得最好的软件体验。虽然该方法能够使程序在新架构
上直接运行，但是如果在没有程序源代码的情况下，对于一些比较老的软件以及
商业级且没有适配意愿的闭源软件都无法通过该方法来完成。
第二种方法是采用二进制翻译技术，来在 LoongArch 平台上直接运行 X86 的

1.2

安卓运行时相关技术

“运行时”（Runtime）最早起源于编程语言的执行阶段 [4] 。当程序编译成机器
语言后，它需要一个环境来执行该代码，这个环境就是运行时。早期的计算机程序
通常由开发者手动管理内存、输入输出等资源，但随着计算机硬件和软件的不断
发展，操作系统和语言设计逐渐引入了更为自动化的运行时环境。为了简化开发
流程，程序员不再需要关心底层细节，运行时开始承担更多的责任，如内存分配、
垃圾回收、线程管理等，这一变化大大提升了开发效率和程序的稳定性。

运行时的功能和作用可以归纳为提供程序执行的基本服务、管理系统资源以
及为开发者提供高级抽象。运行时不仅负责管理内存和硬件资源，还处理程序的
动态链接、异常处理和库函数调用等。它是程序与操作系统之间的桥梁，确保程序
在不同硬件和操作系统平台上的兼容性。此外，现代编程语言中的垃圾回收、虚
拟机支持（如 JVM、.NET 等）也是运行时的一部分，它们通过自动化管理内存和
优化性能，进一步简化了开发流程。因此，运行时在现代软件开发中扮演了不可
或缺的角色。本章将介绍安卓操作系统和安卓运行时，然后介绍实现安卓运行时
在新架构中移植和优化所需做的相关工作。

1.2.1

安卓

安卓操作系统（Android）是由 Google 主导开发的开源移动操作系统，自 2008
年推出以来，安卓系统迅速成为全球最广泛使用的智能手机操作系统之一。安卓
使用 Linux 内核，同时为了规避 Linux 的 GPL 协议，安卓重新写了一套 libc 库，称
为 bionic，因为运行于此库之上的程序可以遵从 BSD 协议，同时也能针对性的对
移动设备进行优化。
在 Bionic 之上有一层硬件抽象层（Hardware Abstraction Layer, HAL）, 其提供
了一种接口，使得安卓操作系统能够与不同的硬件平台（如摄像头、显示器、音频
设备等）进行交互。每个硬件模块有对应的 HAL 接口，安卓可以通过这些接口与
硬件设备沟通，而不需要直接操作硬件。
在 HAL 与 Framework 之间就是安卓系统库，其包括一个运行 Java 语言所需
的安卓运行时，以及所有为应用程序提供支持的核心库，如 OpenGL ES（图形处
理）
、SQLite（数据库管理）
、WebKit（浏览器引擎）等。通过这些库，开发者能够
利用安卓提供的丰富功能来构建应用程序。
再往上的 Framework 层是安卓操作系统中关键的一部分，其提供了应用程序
开发所需的 API 和系统服务。它包括如 Activity、Service、Content Provider、Broadcast
Receiver 等组件，帮助应用程序进行界面显示、数据存储、通讯等操作。此外，框
架层还包括图形、位置、传感器等各种系统服务，帮助开发者快速访问硬件设备
和提供各种功能。
顶层是用户应用程序层，所有的用户应用（如短信、相机、浏览器、邮件等）
都运行在这一层。安卓操作系统为开发者提供了强大的 API 接口，允许开发者构
建丰富的应用程序。所有应用程序都运行在 ART 虚拟机中。因此，ART 在整个安
卓操作系统中扮演着不可或缺的角色，没有它所有的安卓应用程序都将无法运行。
经过十几年的发展，安卓已经成为全球最主流的移动操作系统之一，广泛应
用于智能手机、平板电脑、智能电视、车载系统以及物联网设备。凭借其开源特

1.2.2

安卓运行时

ART 前身为 Dalvik VM [6] 。与绝大多数基于栈的虚拟机不同，Dalvik VM 是基
于寄存器的虚拟机，这一设计的主要原因是为了针对移动设备的性能优化。相比
栈式虚拟机，寄存器虚拟机减少了指令执行时的栈操作，可以更高效地利用 CPU
寄存器，从而在减小运行时内存消耗的同时提高指令执行速度。Dalvik VM 并不遵

循 Java 虚拟机规范，而是自己重新设计了一套适用于移动设备的虚拟机规范。其
使用 DEX 作为专为寄存器架构优化的字节码格式，支持更少的指令、更高效的执
行，并能减少内存占用。
在 Dalvik VM 的发展初期，其只支持逐条解释执行 DEX 字节码；在 Android
[7]
2.2 中，谷歌将即时编译（Just in time，JIT）

预编译技术。

能够在程序安装的同时就将 DEX 字节码全部本地编译成本地机器码，极大提高应

然而 AOT 也不是万能钥匙，当启用 AOT 进行安装程序的时会造成卡顿以及

2.1.1 DEX 字节码
DEX（Dalvik Executable）字节码最早起源于 Android 生态系统的发展需求。在
2005 年，Google 收购了 Android Inc.，并开始打造一个全新的移动操作系统 [12] 。为
了扩展其生态，谷歌选取了当时正火热的 Java 来充当其应用程序的开发语言。在
[13]
当时的移动计算环境下，传统的 Java 虚拟机（JVM）
并不适用于移动设备。同

时为了摆脱当时 JVM 许可证的商业限制，谷歌自己设计了一套针对移动设备优化
的 DEX 字节码。相比于传统的电脑，移动设备在 CPU、内存、功耗的资源上更有
限，因此，在 Java 字节码的基础上，DEX 字节码在多个方面进行了优化。
安卓虚拟机与 JVM 最大的不同就是 JVM 是栈式虚拟机，而安卓是寄存器式
虚拟机。栈式虚拟机在执行计算时，需要先将操作数压入栈中，计算完成后再从栈
中弹出结果。由于其指令采用零地址格式，相较于其他形式的指令更加紧凑，因
此特别适用于存储资源有限的硬件环境。相比之下，寄存器式虚拟机的工作方式
则有所不同，它可以直接对寄存器中的数据进行显式操作，减少了栈操作的开销，
从而提高了执行效率 [14] 。因此，在表示同样程序逻辑的情况下，栈式虚拟机会生
成比寄存器式虚拟机更多的指令条数。通过图 2.1的简单示例可以看到，当进行一
些基本的运算时，栈式虚拟机需要首先到内存中读取数据，然后再对读取出的数
据进行运算。而寄存器式虚拟机可以直接操作寄存器，因此不但减少了指令条数，
同时也减少了访存操作，使得寄存器式虚拟机有着更高的运行效率。安卓虚拟机
的这个特点，极大的促成了其在资源有限的移动设备上能够高效的运行。

字节码解释器

2.1.2

在 Android 4.4 及更早版本中，Android 使用 Dalvik VM 作为运行时环境，DVM
主要依赖解释执行 [16] 。与编译执行不同，解释器不会将字节码转换为本地机器码，
而是通过解释的方式直接执行 DEX 字节码指令。一开始的字节码解释器只具备
C++ 模板解释器的功能，其运行效率比较低下。当使用 ART 代替 DVM 后，在
Android 7.0 版本中，通过引入 mterp（modular interpreter）汇编解释器来大大提高
了字节码解释器的效率。在 Android 11.0 版本中，谷歌引入了更加激进的 nterp 汇
编解释器来再次大幅提高 ART 的冷启动和字节码解释速度。接下来将分别介绍这
些技术。
安卓运行时中的 C++ 字节码解释器采用简单的 switch-case 方式执行，每条
字节码的执行流程包括取指（Fetch）、解码（Decode）、分派（Dispatch）和执行
（Execute）
，这一完整的执行周期被称为一次 FDX 循环。由于寄存器式虚拟机的字
节码指令数量较少，相应地 FDX 循环的执行次数也减少，从而降低了解释开销，
提高了解释器的执行效率。基于全使用 C++ 代码进行解析、解释 DEX 字节码的特
性，且所有要处理的数据都放在虚拟寄存器中，所以其在处理数据的时候就会有
许多 load store 的操作，造成运行效率的低下。因此，虽然 C++ 解释器拥有较高的
可移植性，但其运行特点造成了性能的不足。

整体系统的内存使用效率，尤其是在移动设备资源受限的情况下更具优势。同时，
由于 ART 的 JIT CodeCache 只分配执行权限，避免了可写可执行（W+X）区域的
存在，也在一定程度上增强了系统的安全性，减少了潜在的攻击面。
2. AOT 编译器
在 ART 中，除了 JIT 编译器用于运行时优化，其还引入了提前编译（Aheadof-Time, AOT）机制 [21] ，以进一步提升应用的启动速度和执行效率。AOT 编译主
要发生在应用安装阶段，它通过对应用的 DEX 代码进行静态分析和优化，并将其
转换为更高效的机器码存储在设备上，从而减少运行时的编译开销。相比于 JIT 编
译仅在热点代码上进行优化，AOT 编译对整个应用的代码进行静态转换，这种方
式尤其适用于移动设备，因为它能够在应用首次启动前就准备好高效的本地代码。
ART 的 AOT 编译器主要基于 dex2oat [22] 工具，它会在应用安装或系统更新时

2.1.4

编译优化技术

在 ART 的运行过程中，其会根据代码、运行路径的不同做许多不同的编译优
化工作，来提升系统和应用运行时的效率。除谷歌本身的工作为，也有许多团队
为其进行了相关的优化尝试。Samsung 在 ART 的 JIT 编译过程中探索了一种结合
机器学习的配置感知型优化策略，该方法利用随机森林（Random Forest）模型对
运行时收集的性能剖面数据进行建模，从而指导 JIT 编译器在特定场景下生成更
优的中间表示与目标代码 [24] 。来自复旦大学的团队提出 JavART，通过构建一个规
则驱动的 JIT 编译器，能够在运行时直接生成高质量的本地代码，跳过解释执行阶
段与初级优化阶段，从而显著降低延迟 [25] 。
本节将选取几个较为常见和经典的编译优化技术进行剖析，包括常量折叠，死
代码消除，栈上替换，内联优化等进行介绍。
1. 常量折叠和死代码消除
常量折叠和死代码消除都有非常悠久的历史，它们的诞生可以追溯到最早期
16

北京交通大学硕士学位论文

相关技术

的编译器发展阶段。到如今这两项技术已经发展的较为成熟 [26] 。在编译优化的初始
阶段，ART 通过常量折叠（Constant Folding）和死代码消除（Dead Code Elimination）
等技术，对代码进行初步精简。常量折叠是一种编译期优化技术，编译器会在代码
编译阶段计算出所有能确定值的常量表达式，并用计算结果替换原表达式，从而
减少运行时计算开销。例如，int x = 2 + 3; 在编译阶段会被直接替换为 int x = 5;，
避免了运行时的加法操作。此外，布尔逻辑表达式也会被优化，如 boolean f lag =
true && f alse; 会被直接替换为 boolean f lag = f alse;。常量折叠不仅能减少不必
要的计算，还能暴露更多优化机会，例如后续的条件分支优化和死代码消除。
死代码则通过控制流分析和数据流分析识别永远不会执行的代码块，它会检
测程序中不会影响执行结果的代码并将其删除，以减少代码体积，提高执行效率。
例如，未被使用的变量赋值会被移除，如 int x = 10; x = 20;，由于 10 从未被
使用，因此 int x = 10; 这行代码会被消除。类似地，对于恒定条件的分支，如
i f ( f alse) x = 20;，整个 if 语句都会被移除。结合常量折叠，死代码消除可以进
一步优化代码，比如 i f (3 ∗ 4 == 10) 经过常量折叠变成 i f (12 == 10)，进而识别
为不可达代码并被删除。ART 会在 JIT/AOT 编译初期执行死代码消除，从而减少
无效指令，提高运行时性能。

[27]
是一种在运行时替换正在运行的
栈上替换（On-Stack Replacement，OSR）

函数/方法的栈帧的技术，主要用于在方法执行过程中将低优化级别的代码动态替
换为高优化级别的代码，以提高执行效率，或是将代码从高优化级别回退到低优
化级别，以满足某些调试，异常处理等情况的需求。其思想起源于上世纪 90 年代，
最初是为了满足调试高优化级别的代码而出现的 [28] 。后来经过长期的发展，OSR
慢慢称为一项成熟且有效的技术，并且将从高优化-> 低优化和低优化-> 高优化都
称为 OSR。
在 ART 中，通常是以方法为单位来进行 JIT 编译，当一个方法在编译好之后，
要等到下一次被调用时候才能被用上。对于某些局部性很热的方法来说，OSR 对性

运行此类代码的同时遇到调试或者异常，那么执行引擎也会 deoptimize 到原来的

3. 内联优化
内联优化也是 JIT 编译器用来提高方法调用性能的重要手段之一，其核心思
想是将将小函数的代码直接插入到调用点，避免额外的函数调用开销，以提高执
行效率。在最早期的编译器中，人们主要采用手工内联的方式来优化函数 [29] ，之
后随着编译器的发展，自动内联技术在主流编译器中逐渐出现 [30] ，但此时的内联
主要都是一些静态函数的内联。在 JIT 编译技术出现以后，内联优化技术又迎来了
一个全新的发展，在运行时分析热点代码并进行动态内联，又在很大程度上为解
释型语言提升了运行的效率。
JIT 编译器主要会通过三个步骤来实现内联优化。首先其会识别当前的函数调
用是否符合内联规则，该规则主要是基于方法是否足够小、是否含有递归调用、被
调用方法是否是 ﬁnal、private、static 以及是否有 $inline$ 或 $noinline$ 的标记等。
如该方法为可内联方法的话就会进入到下一阶段生成内联代码。在该阶段中实际
上是将被调用方法的 IR 复制进调用点，插入新的基本块，并重新连接控制流图
（CFG）
。最后一步就是将原来的 HInvoke 指令会被替换成内联后的代码块，控制流
和数据流也要更新，从而完成整个函数的内联。

是在两个世界之间达成一个调用惯例共识。调用惯例定义了如何传递参数和返回

求的栈帧信息。为了支持 JNI，ART 应该了解 C 的调用惯例，然后使用 JNI 来充
当桥梁，统一起高级代码和本地代码之间的调用约定。
在 ART 处理 Java 代码时，当遇到对本地方法的调用，它会生成一条调用封装
代码（如 JNI_trampoline）的指令，充当 Java 调用方与本地代码之间的桥梁。封装
代码遵循 Java 方法的调用惯例，以确保从 Java 端来看，本地方法的调用方式与普
通 Java 方法一致，同时也符合本地调用惯例，以保证正确执行。为此，封装代码
需要完成参数的准备与恢复，确保方法调用时数据能够正确传递和返回；提供栈
[33]
展开（stack unwinding）
支持，使调用栈在异常或返回时能够正常展开；处理垃

圾回收（GC）机制，确保本地方法对 Java 堆的访问不会干扰 GC 的正常工作；支
持异常处理，使本地方法可以抛出或捕获 Java 异常并正确传递；同时提供同步支
持，确保多线程环境下的安全性。通过这一系列机制，封装代码使本地方法的调

正确合并，使其符合本地方法的调用要求。在 ART 的 JNI 实现中，Java 调用
方最初准备的栈布局会被完整保留，并在封装代码返回时进行清理。
4. 寄存器与同步支持：在保存栈的同时，还需保存被调用方的保存寄存器（calleesaved registers），以确保执行环境的完整性。此外，为了支持同步机制，封
装代码在调用本地方法前后会插入 monitorenter 和 monitorexit 等同步检查指
令，确保多线程环境下的正确性与安全性。
最终，通过这一系列操作，高级语言才能顺利过渡到低级语言，实现方法调
用的无缝衔接。同样，从低级语言返回到高级语言的过程也遵循类似的原则，确
保调用惯例、栈布局和执行环境的正确性，使跨语言调用平稳高效地进行。

C++ 解释器更多用于为调试与可观测性工具提供完整的语义支持。其在平台

在 Nterp 中采用了 compute-to 的方式对字节码进行逐条执行。具体实现上，系
统将每一条字节码对应的汇编解释逻辑限制在 128 字节以内，并使用一个专用寄
存器 xIBase 来保存解释器指令表的基址。执行过程中，解释器首先从 DEX 文件中

升了 CPU 的指令流水效率并降低了分支预测失败的开销。
汇编解释器原生为 X86 与 ARM 架构设计，广泛依赖 X86 和 ARM 特有的高

3.3

无论解释器的效率再高，其也永远只能单条顺序解释 DEX 字节码，永远无法

在实现 ARTOL 的过程中，代码生成器的构建包括多个子模块：汇编器负责将
发射出的汇编代码转换为机器码，反汇编器用于将生成的机器码反汇编为 LoongArch 汇编代码，用于后期程序的调试，指令生成器用于将高级中间表示映射至具
体指令语义，链接器用于将生成的跳转指令中的目标地址进行重定位并进行绑定，

这些组件不仅需满足 LoongArch 指令集架构的设计规范，还需与 ART 编译框架深
度融合，确保 ARTOL 能够正确实现。
本节将从汇编器 & 反汇编器、汇编器测试框架、链接器、指令生成器几部分

3.3.2

汇编器测试框架

汇编器测试框架在 ARTOL 实现的过程中扮演着关键验证工具的角色。其主要
目的是验证汇编器生成的机器码是否在语义上准确且编码正确，确保每一条目标

编译器的代码生成高度依赖汇编器接口，任何编码错误都可能在运行时导致逻辑
错误、性能退化，甚至崩溃，因此构建覆盖全面、易维护的测试集也是实现 ARTOL
中不可或缺的一环。

至少有一条测试样例。对于每一条指令，都应该通过构造极端参数值（如立即数
字段的最大最小值、寄存器号溢出、符号位截断、对齐边界等）来测试汇编器实
现的正确性，提前有效揭示汇编码路径中潜在的位段截断、非法编码、符号扩展
错误等问题。为了验证分支跳转类指令在极限范围内的编码正确性，测试集中特

3.3.4

指令生成器

在 ART 中，除了 DEX 字节码之外，在 DEX 字节码与汇编代码之间引入了一
个高级中间表示 HIR（High-level Intermediate Representation），其比 DEX 字节码
有着更丰富的语义信息，如 HAdd, HLoad, HDeoptimize, HInvokeStaticOrDirect 等，
同时又保持了平台无关性，可以方便的映射到多个目标架构平台。HIR 保留了程
序的控制流和数据依赖信息，也提供了足够的抽象以进行高级优化，如常量传播、
死码消除等。
在 ART 中，许多编译优化都可以在 HIR 层面进行。首先，代码生成器会将
Java 代码按方法分块，会将每个方法中的 dex 字节码解析成 HIR，然后这些 HIR
会组成一个 HGraph，HGraph 是承载 HIR 的主要数据结构之一，代表着待编译方
法的控制流与数据流语义的完整抽象。每个方法在被转换为 HIR 后，会被构造成
一个 HGraph，其中的节点（HInstruction）对应程序的操作单元，而图中的边表示
数据依赖与控制依赖。HGraph 不仅具备显式的基本块结构（HBasicBlock），支持
显式建模分支与跳转语义，而且由于其采用 SSA（静态单赋值）形式，天然适合进
行数据流分析与表达式优化。相比原始 DEX 字节码的线性表示，HGraph 提供了
更加结构化和优化友好的基础，使得编译器可以以图为操作对象，执行跨基本块
甚至跨路径的高层优化。常量传播、死代码删除等编译优化都在 HGraph 层完成。
这些优化依赖 HGraph 所提供的 SSA 属性与图结构遍历机制，使得编译器能够在
保持程序语义不变的前提下，最大限度地简化指令序列并提升运行时性能。更重
要的是，HGraph 完全独立于目标架构，其所承载的优化具有良好的可移植性和重
用性。
在完成多个编译优化阶段后，经过规约与重写的 HGraph 会进入指令生成前的
控制流布局阶段。在此阶段，编译器依据控制流图中显式建模的跳转与分支关系，
将 HGraph 划分为若干基础块（Basic Blocks）
，即 HBlock 的集合。每个 HBlock 对
应程序中的一个控制流片段，通常以跳转、条件分支或函数返回语句作为结束节
点。这些 HBlock 之间通过边界跳转指令（如条件转移 if, 无条件跳转 goto 等）构
建完整的控制流图（Control Flow Graph, CFG），使得编译器能够在保持语义等价
的前提下，精确掌控代码布局与分支优化策略。

3.4.1

快速路径

在 ARTOL 的实现过程中，运行时系统中广泛使用了一系列以 art_quick_ 前缀
命名的函数。这些函数代表了 ART 针对高频率、性能敏感操作所设计的“快速路
径（quick path）”执行机制，旨在为方法调用、对象分配、异常处理、字段访问
等关键操作提供高效、平台特化的支持。相比之下，传统意义上的“慢路径（slow
path）”则处理低频或复杂情形，如类尚未初始化、类型解析失败等。然而，随着
ART 体系的演进，大量原本独立的 slow path 逻辑已被内联或集成进 art_quick_ 函
数内部，通过调用高级语言（C++）实现的 fallback 分支处理异常或边界情况。
在系统初始化阶段，ART 通过 quick_default_init_entrypoints.h 中的注册函数
DefaultInitEntryPoints，将通用逻辑层的函数指针与架构相关的汇编符号绑定，确

3.5

尽管 ART 提供了丰富的运行时信息和日志机制，但其多层次执行模型本身也
为调试带来了显著挑战。首先，目前在 ARTOL 中同时支持 C++ 解释器、Nterp 汇

桥接代码往往在 native 层崩溃，而 native 调试器难以准确回溯 ART 虚拟栈，进一
步增加了问题定位难度。特别是在调试龙架构适配过程中，缺乏完善的工具链支
持也限制了符号信息的解析与指令级行为的对比分析。因此，实现一个统一可用
的调试框架对于 ARTOL 的可维护性和实现正确性具有重要意义。

3.5.2 JIT 编译路径
不同于字节码解释器严格逐条执行、语义路径高度确定的特点，JIT 编译器的
调试过程通常更具挑战性。一方面，JIT 编译过程涉及诸多动态因素，如热点探测
策略、常量传播、分支预测优化等，这些都会对生成代码的结构与行为产生直接
影响。因此，同一段 Java 代码在多次运行过程中，其实际生成的机器码往往并不
完全一致。另一方面，JIT 编译器在生成中间表示（HIR）及最终代码时并不严格
遵循字节码的线性顺序，某些字节码指令在高等级优化策略下可能被省略、合并
甚至替换成完全不同的实现逻辑，从而使得传统的逐条比对方式不再适用。这种
“优化即重写语义”的特性使得错误定位的路径极其复杂，也增加了调试工具设计
的难度。
为了解决上述问题，ARTOL 采用了一种控制变量与可视化相结合的调试策
略，以提升 JIT 编译器路径的可调试性。首先，在运行测试用例时，ARTOL 显式
启用–jit-on-ﬁrst-use 编译选项，通过将热点门槛设置为 0，强制系统在方法首次调
用时立即触发 JIT 编译。这一策略显著减少了编译触发的不确定性，使得每次运行
相同 Java 程序时生成的机器码在大多数情况下保持稳定，从而为构建可复现的调
试场景提供了条件。
其次，为了清晰展示 JIT 编译过程的中间状态，ARTOL 借助前文实现的反汇
编器，并通过–run-test-option=’-Xcompiler-option –dump-cfg=result.txt’ 参数导出每
个被 JIT 编译的方法的控制流图（CFG）。该控制流图以文本形式记录了每个 Java
方法的基本块（HBasicBlock）
、中间表示（HIR）节点、最终生成的汇编指令，以
及它们之间的映射关系。例如，对于一个包含条件分支的方法，CFG 输出能够标
明某个 HIf 条件对应的机器指令地址范围，从而在程序崩溃或异常行为出现时，可
以通过栈回溯得到的 PC 地址逆推出触发问题的语义节点。这种地址与语义的一
一映射机制，为逻辑层面的错误排查提供了极大的便利。

4.2.1 JNI 编译优化
在原有的 ARTOL 中，所有的 JNI 调用都默认统一通过通用跳板函数，也就
是 art_quick_generic_jni_trampoline 进行分发和处理，该设计在系统层面提供了高
度的通用性和健壮性：通过一套统一的调用路径，ART 能够支持任意签名的本地
方法。但是从性能角度来看，这种“一刀切”的处理方式固然保证了调用语义的完
整性，但在面对高频且签名稳定的 JNI 方法时，其运行时开销却成为了系统性能
瓶颈之一。为进一步优化 ARTOL 的 JNI 调用性能，本文对机器码执行时的不同的
JNI 方法进行了不同的定制化处理，依据方法签名、传入参数等生成高度定制化的
调用代码，以绕过通用跳板函数的性能开销，提升 JNI 的调用效率。
实现该优化的关键，就是要为 JNI 调用实现一个编译器，通过该编译器可以
为每种参数类型生成特定的跳板函数，由于这些特制的跳板函数知道了函数的参
数类型，因此在进行参数转换、传递时更加直接高效。同时，此处的参数类型可
以表示为不同的返回类型，如下两个函数的代码所示，第一个参数都为引用类型，
第二个参数都为 4 个字节的基本类型，因此这两个函数可以共用同一个 JNI 跳板
函数，此时 JNI 编译器也可以对跳板函数进行复用，提升系统的运行效率。

从安卓 8.0 开始，ART 中引入了两种更为快速的 Native 方法，分别为 @FastNative 和 @CriticalNative [43] ，使用这两个注解可以加速对 JNI 函数的原生调用。
@FastNative 是一种相较于标准 JNI 更加轻量级的调用路径。其核心优化在于避免
了 JNIEnv* 与访问控制表之间的部分交互，从而降低了上下文切换与堆栈准备的
开销。与标准 JNI 方法一样，@FastNative 方法仍然允许使用 JNIEnv* 来访问 Java
对象、类字段或调用其他方法，但 ART 会对其调用路径进行优化，减少调用过程
中的锁竞争与线程状态切换。相较之下，@CriticalNative 是一种更为激进的优化机
制。其最大特点是完全绕过了 JNIEnv* 环境和线程状态切换机制，使得方法调用
的开销趋近于纯 C/C++ 层函数调用。两种方法对比如表4.5所示。在实现 JNI 编译
器的过程中，有大量的工作在进行这两种方法的适配，只有实现了这两种调用方

数，通过 18 个步骤来实现 JNI 调用函数的编译功能，在每一步骤中都会生成对应
的 LoongArch 指令。下面对其进行一一讲解。
1. 构建方法调用栈帧。首先，为当前方法构建栈帧，包括保存所有 callee-saved
寄存器、ArtMethod* 指针、返回地址等信息。对于 @CriticalNative 方法，额外分
配参数传递空间；而非 CriticalNative 情况下，只需分配常规托管帧。
2. 写入栈顶指针。对于常规 JNI 和 @FastNative 方法，需将栈顶指针写入
Thread::TopOfManagedStack 字段，以便在发生 GC 时正确记录调用栈。而 @CriticalNative 方法无需此操作，因其在执行期间禁止 GC。
3. 为出参扩展栈帧。为 native 方法调用的出参区域扩展栈帧。@CriticalNative
方法已在帧构建阶段分配完成，常规情况则需要动态扩展栈帧。
4. 进行读屏障的判定。若启用 Read Barrier（如启用并发 GC），并且为 static
方法，则需要判断是否进入 slow path，因为 jclass 传参需经过读屏障修复。该流程
对 @CriticalNative 方法跳过，因为其不传递 jclass 参数。
5. 进入 JNI 方法起始逻辑。该步骤中需要实现调用 JniMethodStart 函数，传递
Thread 指针以促进从 Runnable 状态的转换。此调用返回保存的 JNI 本地状态，将
由退出调用恢复。
6. 填充参数。设置并传递 Java 参数至 native 方法。对于 @CriticalNative 方法，
参数传递路径经过极致优化，避免 JNI 类型封装，直接以机器本地类型传递。
7. 处理 static 方法的 jclass 参数。若为静态方法，需提供其声明 jclass 类指针
作为参数。对于 @CriticalNative 方法则跳过该处理。
8. 创建 JNIEnv* 参数。常规 JNI 方法需构造并传递 JNIEnv* 参数，而 @CriticalNative 路径中完全省略该参数以提升调用性能。
9. 原生代码调用。此步骤用于实现使用 JNI 入口点的偏移量来植入与方法关
联的原生代码的调用。
10. 返回值位宽对齐。当 native 返回类型为 byte、short、char、boolean 等窄类

型时，此步骤中将对其执行零扩展或符号扩展操作，以确保类型安全。
11. 保存返回值。若返回值将被 JNI 方法 JniMethodEnd 退出逻辑覆盖，则需在
调用后将返回值临时保存于栈中。此步骤对 @CriticalNative 跳过。
12. 调用 JniMethodEnd。恢复线程本地引用状态，对于同步方法来说，还需释
放 monitor 锁。此外还传递返回值以及同步解锁所需的 this 或 jclass 参数。
13. 返回值重载。对于已保存的返回值，重新从栈中加载至返回寄存器。此步

14. 参数使用后调整栈帧。处理完输出参数后，对于非 @CriticalNative 方法，栈
帧大小会减少。对于 @CriticalNative 方法，输出参数与栈帧一起在 RemoveFrame()
中移除。
15. 异常处理。对于非 @CriticalNative 方法，进行异常轮询以处理来自 JNI 调
用或监视器退出的待处理异常。
16. 移除栈帧并恢复保存的 callee-saved 寄存器。CriticalNative 方法因不支持线
程挂起，在此的执行路径略有不同。
17. 静态调用的读屏障慢路径设置。若第 4 步中进入 slow path，此处进行栈帧
修复，并调用 runtime 中的 ReadBarrierJni 修复 jclass 引用。之后跳转回正常路径继
续执行。
18. 完成代码生成。最终完成指令流的生成，并完成 JNI stub 的构建。
最终，通过上述十八个步骤的构建过程，ARTOL 的 JNI 编译器在运行时成功
生成了完整的 JNI stub，涵盖了从方法帧的构建、参数传递、JNI 环境准备、调用
路径管理、返回值处理到异常回收等各个关键环节。在此基础上，JNI 编译器进一
步对 @FastNative 与 @CriticalNative 方法的调用路径进行了特殊优化：前者通过精
简线程状态过渡与本地引用管理逻辑，有效减少了进入 native 方法的开销；后者
则更进一步，完全绕过了线程状态登记与 GC 安全点设置，直接以寄存器快速传
参的方式实现原生调用，最大限度降低了 JNI 调用的执行成本。这一优化不仅保
障了调用语义的正确性，还在性能敏感场景下显著提升了 native 方法的调用效率，
为高频 JNI 接口提供了更优的运行时支撑机制。

内联优化

内联（Inlining）是编译器中最基础且广泛应用的优化之一，其核心思想是将方
法调用替换为方法体本身，从而消除调用开销。本小节将遵循其思想，为 ARTOL
添加内联优化。在本节对 intrinsic 方法的优化处理中，内联不仅仅是控制流层面的
展开，更表现为一种将高层语义压缩为一个低开销中间表示节点的机制，在某种
意义上相当于一种“超级字节码”（Super-Bytecode）。以 Math.sqrt(double) 方法为

本章小结
本章围绕 ARTOL 的正确性与性能表现，进行了全面的测试与分析，并在此基

础上提出并实施了多项系统性优化措施以提升其在实际运行环境中的执行效率。
首先，在正确性方面，通过一系列功能测试与基准验证，确保 ARTOL 在支持
JNI 调用、字节码执行及相关运行时行为方面与预期语义保持一致，验证了其在龙
架构平台上运行的可行性与稳定性。
其次，在性能优化方面，本文从三条关键路径出发，对 ARTOL 进行了有针对
性的系统优化：
（1）针对不同类型的 JNI 方法，引入了专用的 JNI 编译器，能够对
@FastNative 与 @CriticalNative 等轻量级本地方法进行定制化编译，避免通用 JNI
接口中繁重的封送与上下文切换开销。实测结果表明，相比通用 JNI 方法，这类
优化后的调用路径可带来 3 5 倍的性能提升；
（2）针对包含大量方法调用的程序场
景，ARTOL 引入了基于 JIT 的内联优化机制，对热点路径中的短小函数进行内联
展开。以 CaffeineMark 基准测试为例，开启内联优化后，ARTOL 的整体得分相比
未优化前提升了 35.37%，其中与方法调用频率密切相关的 Method 子项甚至获得
了近五倍的性能提升；
（3）对于执行过程中包含大量循环的函数，ARTOL 添加了
OSR 栈上替换机制，使得解释执行过程中可以在合适时机切换至已编译的机器码，
显著降低循环执行开销。实测表明，该机制可带来平均 23.05% 的性能提升。
综上所述，本章通过系统性测试与有针对性的优化设计，从 JNI 接口、方法调
用路径与循环执行三个典型热点场景出发，有效提升了 ARTOL 的执行效率与响
应能力，同时也保证 ARTOL 实现的正确性和可靠性。

总结与展望

第 5 章 总结与展望
5.1

总结
作为一款新兴的国产指令集架构，LoongArch 在架构设计上具有自主可控、简

洁高效等诸多优点，然而其面临的最大挑战之一是软件生态尚不完善，特别是在
移动应用和嵌入式系统方面仍处于起步阶段。针对这一问题，本文提出并实践了
一种可行的解决方案：实现龙架构上运行的安卓运行时 ARTOL，以适配大量现有
的安卓应用程序，推动其生态扩展。
本文主要工作和贡献如下：
首先对运行时技进行术调研与体系结构分析。系统性调研了当前现有的安卓
运行时技术，深入分析了安卓中 ART 的整体架构及其在不同指令集平台上的实现
机制，以及安卓运行时的 DEX 字节码与 Java 字节码的对比。通过对其核心组件，
包括解释器、JIT 编译器、JNI 接口等的功能与交互关系的梳理，为后续在龙架构
平台上的移植与重构工作奠定基础。
二是在龙架构平台下进行了安卓运行时的设计与实现。面向 LoongArch 指令
集架构，设计并实现了完整的安卓运行时系统，涵盖了从字节码执行到机器码生
成的关键执行路径。具体包括：基于 C++ 实现的通用解释器、基于汇编的 Nterp
快速解释器、JIT 编译器子系统，其中包括汇编器、反汇编器、链接器和指令生成
器等关键组件，以及运行时的支持，同时为不同执行方式搭建了不同的调试框架。
确保了安卓应用在新架构平台上的正常运行与性能表现。
三是对 ARTOL 子模块进行针对性优化。具体包括引入专用的 JNI 编译器，对
@FastNative 与 @CriticalNative 方法进行特化编译，以此降低 JNI 调用的开销；为
ARTOL 添加函数调用内联优化，以减少函数调度成本；面向长时间运行的循环结
构，集成了 OSR 机制，实现从解释执行到编译执行的平滑过渡，提升循环密集型
程序的运行效率。这些优化手段覆盖了运行时的不同层级，可以有效提升系统整
体性能。最后进行系统性的正确性验证与性能评估。在完成运行时各模块的设计
与实现之后，本文对 ARTOL 系统进行了全面的测试与评估。通过功能性测试验证
其在龙架构上运行与其它平台运行的语义一致性与稳定性，表明了 ARTOL 实现
的正确性与稳定性。并借助 CaffeineMark 等标准基准测试对系统性能进行了定量
分析。测试结果表明，优化后的 ARTOL 在多个典型场景下均表现出显著的性能提
升，验证了所提出优化策略的有效性与实际应用价值。

5.2

总结与展望

展望
尽管本文在龙架构平台上成功实现了 Android 运行时系统 ARTOL，并在解释

器、JIT 编译器以及关键路径优化方面取得了良好的实验效果，但仍存在若干值得
进一步研究与完善的方向，未来可从以下几个方面开展深入工作：
首先，当前 ARTOL 主要实现了解释执行与 JIT 编译路径，尚未涵盖 AOT
（Ahead-of-Time）编译功能。AOT 编译对于减少应用冷启动延迟、提升嵌入式场
景下的资源利用效率具有重要意义。后续工作可在 LoongArch 架构上扩展 dex2oat
工具链，实现 AOT 后端的支持，进一步完善运行时的执行体系。
此外，本文工作基于特定版本的 AOSP 实现，尚未开展大规模安卓应用兼容
性测试。随着安卓系统版本的快速演进，未来可将 ARTOL 平台迁移至更高版本的
安卓系统，并建立自动化的兼容性测试框架，以确保其在实际应用场景中的适配
性与稳定性。
最后，本文所实现的 ARTOL 目前主要支持运行纯 Java 编写的应用程序以
及包含使用 LoongArch NDK 工具链编译生成的本地动态库的应用，基本满足了
Android 应用在新架构平台上的运行需求。然而，在实际应用场景中，仍有大量主
流 APK 应用集成了基于 ARM 架构的本地动态库，而当前 ARTOL 尚不具备对这
类异构二进制库的兼容能力。因此，未来一个重要的发展方向是在 ARTOL 中引入
二进制翻译机制，以支持 ARM 到 LoongArch 的动态库兼容执行，从而进一步提
升系统的应用兼容性，拓展其在实际生态中的适用范围。
