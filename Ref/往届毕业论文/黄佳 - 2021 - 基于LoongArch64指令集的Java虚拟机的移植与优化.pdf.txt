摘

要

LoongArch 指令集是自主指令系统架构，具有先进性、兼容性和扩展性的特
点。Java 语言是最受欢迎和应用最广泛的编程语言之一。Java 虚拟机是 Java 语
言实现平台无关性、安全性和许多高级语言特性的基础，是 Java 技术体系的核
心。将 Java 虚拟机移植到 LoongArch 指令集架构有助于推动龙芯自主生态的建
立。
本文完成的工作和主要贡献如下：
第一，完成龙芯 LoongArch 64 位 Java 虚拟机的移植。以 OpenJDK8 为基
础，将 Java 虚拟机中和平台相关的部分，如汇编器、解释器和编译器等移植到
LoongArch 指令集架构处理器上。
第二，完成龙芯 LoongArch 64 位 Java 虚拟机的优化。主要包括：1）通过
优化立即数加载函数和使用移位运算指令和双寄存器访存指令优化指令分派，
提高了解释器的翻译性能，使得 Java 虚拟机的启动性能平均提高了 8.94%；2）
通过使用相对 PC 运算指令和调整 CodeCache 虚拟内存映射空间，优化了 Java
虚拟机中的跳转机制，使得优化后的 Java 虚拟机将近 1/3 的字节码对应的汇编
指令条数减少，平均性能提升幅度为 1.59%；3）通过使用多条 LoongArch 基础
指令拼凑出条件传送指令，使得 scimark.monte_carlo 程序的性能提升 71%，分
支误预测率从 2.99%下降至 0.01%。
第三，进行龙芯 LoongArch 64 位 Java 虚拟机性能评测，结果表明：
LoongArch 64 位 Java 虚拟机在同主频 LoongArch 架构处理器相比于 MIPS 架构
处理器的 Java 虚拟机平均性能提升 21.87%，性能最高提升 42.48%。运行在
2.5GHz 主频的 LoongArch 架构处理器的 Java 虚拟机比运行在 1.8GHz 主频
MIPS 架构处理器的 Java 虚拟机平均性能提升 64.70%，性能最高提升 97.06%。
最后，基于优化和性能分析数据，提出了 LoongArch 指令集的改进方向，
包括增加条件传送指令和加法进位指令。本文的研究成果已经集成到龙芯
OpenJDK8 版本库中，并得到了实际应用。

关键词： LoongArch 指令集，Java 虚拟机，OpenJDK8，优化机制

Abstract

Abstract
LoongArch Instruction Set is an autonomous instruction system architecture,
which has the characteristics of advanced, compatibility and expansibility. Java is one
of the most popular and widely used programming languages. Java virtual machine is
the basis of platform independence, security and many high-level language features of
Java language. It is also the core of Java technology system. Porting Java virtual
machine to LoongArch Instruction Set Architecture helps to promote the
establishment of Loongson's independent ecosystem.
The contributions of this thesis are as follows:
Firstly, complete the porting of LoongArch 64 bit Java virtual machine. Based on
OpenJDK8, platform-dependant parts of Java virtual machine, such as assembler,
interpreter and compiler, are migrated to LoongArch Instruction Set Architecture
architecture processor.
Secondly, complete the optimization of LoongArch 64 bit Java virtual machine.
The main contents are as follows: 1) By optimizing the immediate loading function
and using shift operation instruction and double register access instruction, the
interpreter translation performance is improved, and the start-up performance of Java
virtual machine is improved by 8.94%; 2) By using relative PC operation instructions
and adjusting the codecache virtual memory mapping space, the jump mechanism in
Java virtual machine is optimized, which makes the number of assembly instruction
bars corresponding to nearly 1/3 byte codes of the optimized Java virtual machine
reduced, and the average performance improved by 1.59%; 3) By using multiple
LoongArch base instructions to pieced together conditional transfer instructions, the
performance of scimark.monte_carlo was improved 71%, and the branch-miss rate
decreased from 2.99% to 0.01%.
Thirdly, the performance evaluation of LoongArch 64 bit Java virtual machine.
The average performance of the LoongArch Java virtual machine is 21.87% higher

第1章 绪论
国产 CPU 龙芯处理器采用 MIPS 指令集架构。20 世纪 80 年代早期，MIPS
指令集架构从斯坦福大学诞生，是一种采取精简指令集（Reduced Instruction Set
Computing,简称 RISC）的处理器架构。时至今日，MIPS 的部分设计有些过
时，不能完全适合现代的操作系统和 CPU 设计，例如存在跳转指令偏移范围
小、只有 3 种指令格式、仍然保留过时的延迟槽技术等问题。在这样的背景
下，龙芯处理器研究团队（简称龙芯团队）充分考虑先进与兼容需求，构建了
自主指令集架构 LoongArch。
Java 语言[28]是一种面向对象的高级程序设计语言，可用于编写跨平台的应
用程序，目前已广泛应用于网络服务器、桌面系统和移动终端等领域，并在全
世界拥有最大的开发群体。Java 虚拟机是 Java 技术体系的核心，负责对 Java 程
序进行模拟执行，是影响系统性能的关键因素。Java 虚拟机是 Java 实现平台无
关性、安全性和许多高级语言特性的基础，同时也决定了 Java 的性能。
本文基于龙芯平台，进行了 LoongArch 指令集架构[2]上 Java 虚拟机的移植
和优化。本文工作有助于推动龙芯自主生态的建立。

1.1 龙芯 LoongArch 指令集架构简介
LoongArch 指令集是龙芯团队充分考虑兼容需求设计的自主指令系统。
LoongArch 指令集具有先进性、兼容性和扩展性三个特点[1]。先进性是指积极
吸收近年来指令集发展的先进技术成果，适度摒弃一些过时的技术特征；兼容
性是指融合 X86、MIPS、ARM 指令系统的主要特点，高效支持二进制翻译；
扩展性是指 LoongArch 指令槽留有空余，有利于 LoongArch 指令集今后的持续
迭代演进。
LoongArch 指令集架构具有 RISC 指令架构的典型特征。它的指令长度固定
且编码格式规整，绝大多数指令只有两个源操作数和一个目的操作数。它采用
load/store 架构，即仅有 load/store 访存指令可以访问内存，其他指令的操作对
象均是处理器核内部的寄存器或指令码中的立即数。
LoongArch 指令集架构采用基础部分（Loongson Base）加扩展部分的组织
形式，如图 1.1 所示。其中扩展部分包括：二进制翻译扩展（Loongson Binary

Advanced SIMD Extension,简称 LASX）。LoongArch 总共具有 2565 条原生指

HotSpot 虚拟机相关工作

HotSpot 虚拟机经过 20 多年的发展，引入了很多重要的新特性[17]。JDK5

归档文件中，后续 HotSpot 虚拟机运行时将归档文件映射到内存中，以提升
Java 应用的启动速度。JDK6 时引入了分层编译。在分层编译的工作模式出现

将 JDK 分成一组模块，可以在构建时、编译时和运行时进行组合。模块化可以
减少内存开销，减少各种类库、大型应用的开发和维护。JDK9 另外一个重要的
变化是 G1GC 取代了 Parallel GC 成为了 HotSpot 虚拟机中默认的垃圾回收机
制。因为对于大多数用户而言，G1GC 的低暂停时间特性比 Parallel GC 的高吞

类装载子系统从文件系统或者网络中加载 Class 文件载入运行时数据区。
运行时数据区包括五部分：程序寄存器、虚拟机栈、本地方法栈、堆和方
法区。其中程序寄存器、虚拟机栈和本地方法栈是每个线程私有内存区域，而
方法区和堆是所有线程共享内存区域。程序寄存器可以看作是当前线程所执行
的字节码的行号指示器。程序执行过程中，通过改变这个计数器的值来选取下
一条需要执行的字节码指令来完成下一步的操作。虚拟机栈描述的是 Java 方法
执行的内存模型。整个线程执行过程中，每个方法对应着虚拟机栈中的一个栈
帧，方法调用对应着一个栈帧的入栈，方法执行结束对应着一个栈帧的出栈。
本地方法栈与虚拟机栈所发挥的作用是非常相似的，它们之间的区别在于虚拟
机栈为虚拟机执行 Java 方法，而本地方法栈则为虚拟机执行 Native 方法。堆在
虚拟机启动时创建，用于存放对象实例，是垃圾收集器管理的主要区域，因此
也被称为 GC 堆。方法区用于存储已被虚拟机加载的类信息、常量、静态变
量、JIT 编译器编译后的代码等数据。运行时常量池是方法区的一部分，用于存
放编译器生成的各种字面量和符号引用。
垃圾收集器管理运行时数据区中的堆区，负责对象内存空间的分配，并对
无用的对象进行垃圾清空和内存回收。
执行引擎是 Java 虚拟机的核心部件。执行引擎负责将 Java 字节码翻译成本
地汇编代码。执行引擎包括解释器和 JIT 编译器。解释器又分为 C 解释器和模
板解释器。C 解释器将字节码翻译成高级语言 C 语言进行解释执行，因此可以
不做任何修改即可运行在支持 C 编译器的任何平台。模板解释器则是将字节码
直接解释为本地汇编代码。C 解释器由于需要先转换为高级语言 C 语言，再转
换为目标代码，因此解释执行效率更低。与之相反，模板解释器不需要经过中
间过程，直接转换为汇编代码，因此执行效率更高。JIT 编译器将解释器收集到
的热点方法编译成本地汇编代码后执行整个方法。字节码既可以通过解释器执
行，也可以通过编译器执行。Java 程序一开始都是通过解释器执行，解释器在
执行的过程中收集性能信息，统计方法和循环体执行的次数，一旦某个方法或
循环体达到热点阈值，JIT 编译器则将该方法编译成本地汇编代码执行。JIT 编
译执行过程中，发现编译好的本地汇编代码过于激进，如加载了新类后类型继
承结果出现变化，这时也可以通过逆优化退回到解释器状态解释执行。

2.4 编译器移植
HotSpot 虚拟机里内置了两个编译器，分别称为 Client Compiler[22]和 Server
Compiler[23]，或者简称为 C1 编译器和 C2 编译器。C1 编译器有较快的启动速
度，简单地将字节码编译成机器码。C2 编译器比 C1 编译器性能更高，提供了
内联优化[37]、循环展开、DeadCode 删除[35]、分支预测[36]等优化功能。C1
编译器的移植需要涉及到大量公共层代码的修改，且 Java 虚拟机的峰值性能主
要由 C2 决定，本文接下来主要关注 C2 编译器的移植过程。
2.4.1

C2 编译器架构

HotSpot C2 编译器架构[24]见图 2.9，该图展示了 C2 编译器处理一个方法
的步骤。C2 编译器从一个空图开始，在解析字节码的过程中逐步添加节点。当
一个节点被添加后，C2 编译器开始在本地执行一系列优化：常量折叠、标识和
全局值编号[34]。之后，它通过正确地构建方法出口并执行死代码消除使 Ideal
Graph 更清晰。
接下来的步骤是对 Ideal Graph 做全局优化。这些优化不是强制性的，可以
被编译器跳过。在应用迭代全局值编号算法之后，ideal loop 步骤最多执行三
次。ideal loop 阶段进行循环剥离、循环展开和迭代拆分等操作。条件常量传播
是一种优化，它将常量传播和 if 条件结果为常数的条件结合起来。最后，再次
执行迭代全局值优化和 ideal loop 阶段，即可生成优化后的 Ideal Graph。
代码生成阶段首先将 Ideal Graph 转换为特定于机器的 MachNode Graph，然
后通过控制流图建立基本块、执行图形着色寄存器分配，最后经过一些窥孔优
化，即可产生机器码。

3.2.1.2 Label 类
LoongArch Label 类是实现 Java 虚拟机跳转机制的基础，它表示跳转指令的
目标。Java 虚拟机中的宏汇编跳转指令将 Label 对象作为它们的一个参数。
Label 对象有两种状态，分别是 bound 状态和 unbound 状态。所有的 Label 对象
初始化时均为 unbound 状态，通过汇编器中的 bind 方法，为 Label 对象绑定跳
转的目标地址，Label 对象即从 unbound 状态切换成 bound 状态。当编译某条跳
转指令时，若该指令的 Label 对象为 bound 状态，即已知跳转的目标地址，将
该地址填入指令即可。若该指令的 Label 对象为 unbound 状态，即还不知道跳
转的目标地址，此时先将 0 填入指令，等到该 Label 对象通过 bind 方法绑定跳
转的目标地址之后，再将该目标地址写入。这种之后再回填目标地址的方式称
为 patch。patch 有一个最大的特点是，由于编译时不清楚需要填入值的大小，
因此需要考虑该值所有可能的情况，即需要给该值预留一个最大的空间。表
3.9 中的代码取自 Java 虚拟机中的宏汇编指令 bne_long，该段代码展示了 Label

调整 CodeCache 虚拟内存映射空间

⚫ CodeCache
CodeCache 又叫代码缓存，Java 虚拟机生成的所有代码都放在 CodeCache
里。与 CodeCache 相关的 Java 虚拟机参数有三个，分别是
ReservedCodeCacheSize, InitialCodeCacheSize, CodeCacheExpansionSize。
ReservedCodeCacheSize 表示 Java 虚拟机向虚拟内存申请预留给 CodeCache 的
大小，即 CodeCache 最大的容量。InitialCodeCacheSize 表示 CodeCache 初始状
态时的大小。CodeCacheExpansionSize 指 CodeCache 每一次扩展的大小，即当
当前分配的 CodeCache 被填满后，向 ReservedCodeCache 继续申请
CodeCacheExpansionSize 大小的容量。
ReservedCodeCacheSize, InitialCodeCacheSize 和 CodeCacheExpansionSize 的
大小是和架构相关的，在 LoongArch 架构中它们的默认值分别为 48MB，
2496KB，64KB。ReservedCodeCacheSize 的大小可以使用以下这个虚拟机开关

跳转机制的范围。图 3.5 为 Java 线程运行时的一个虚拟内存映射。通过在 Java

的目标地址是存储在寄存器里，因此在调用 jirl 指令之前需要若干条立即数加

3.2.5

小结

原始跳转机制的实现没有充分考虑 LoongArch 指令集的特点，LoongArch
指令集中有相对 PC 运算指令。利用相对 PC 运算指令，结合优化 CodeCache 内
存布局，使得 128GB 范围的相对地址跳转能够覆盖 LoongArch 64 位 Java 虚拟
机的所有跳转情况。这一优化不仅减少了实现跳转机制的指令，同时消除了绝
对地址跳转。具体的性能效果见 4.3 节。

第5章 总结与展望
5.1 本文工作总结
本文工作主要集中于以下三个方面：
第一，完成龙芯 LoongArch 64 位 Java 虚拟机移植。以 OpenJDK8 为基础，
将 Java 虚拟机中和平台相关的部分，如汇编器、解释器和编译器等移植到
LoongArch 指令集架构处理器上。
第二，完成龙芯 LoongArch 64 位 Java 虚拟机优化。基于性能测试结果和
LoongArch 指令集架构特点，首先通过优化立即数加载函数和使用移位运算指
令和双寄存器访存指令优化指令分派过程，对解释器的翻译性能进行了优化；
接着通过使用相对 PC 运算指令和调整 CodeCache 虚拟内存映射空间对
LoongArch 64 位 Java 虚拟机的跳转机制进行了优化；最后通过使用多条
LoongArch 基础指令拼凑出条件传送指令对 LoongArch 64 位 Java 虚拟机的条件
传送机制进行了优化。
第三，进行龙芯 LoongArch 64 位 Java 虚拟机性能评测。首先对上述三个优
化的优化效果进行了性能评测。经过解释器的翻译性能优化后，Java 虚拟机字
节码对应汇编指令的生成条数相比优化之前下降 18%，同时 Java 虚拟机启动性
能平均增长 8.94%；经过跳转机制优化后，有将近 1/3 的字节码对应的汇编指令
生成条数减少，同时 SPECjvm2008 平均性能提升幅度为 1.59%，最高有 4.24%
的提升；经过条件传送机制优化后，LoongArch 64 位 Java 虚拟机在
scimark.monte_carlo 程序上性能增长高达 71%，同时该程序的分支误预测率从
2.99%降低至 0.01%。接着将 LoongArch 64 位 Java 虚拟机的性能和 MIPS 进行
了对比，结果表明：LoongArch 64 位 Java 虚拟机在同主频 LoongArch 架构处理
器相比于 MIPS 架构处理器的 Java 虚拟机平均性能提升 21.87%，性能最高提升
42.48%。运行在 2.5GHz 主频的 LoongArch 架构处理器的 Java 虚拟机比运行在
1.8GHz 主频 MIPS 架构处理器的 Java 虚拟机平均性能提升 64.70%，性能最高
提升 97.06%。
本文的研究成果已经集中到龙芯 OpenJDK8 版本库中，并投入实际生产。

5.2 龙芯 LoongArch64 位指令集的改进方向
在本文的工作和实验过程中，发现龙芯 LoongArch 64 位指令集在 Java 虚拟
机上有以下两个改进方向：
第一，LoongArch 64 位指令集需要增加条件传送指令。从 3.3 节和 0 节中可
知，进行条件传送机制优化之前，LoongArch 64 位 Java 虚拟机在
scimark.monte_carlo 程序较 MIPS 64 位 Java 虚拟机性能低 30%。目前利用多条
LoongArch 基础指令拼凑出条件传送指令，使 LoongArch 64 位 Java 虚拟机在
scimark.monte_carlo 程序性能增长高达 71%，同时分支误预测率也从 2.99%降低
至 0.01%。若 LoongArch 指令集中有单条条件传送指令，显然会比当前用多条
指令拼凑出的性能效果更好。
第二，LoongArch 64 位指令集需要增加加法进位指令。在与 ARM 机器的
性能比较中，发现 LoongArch 64 位 Java 虚拟机在 crypto.rsa 测试程序中性能较
差，换算成同主频性能只有 ARM 机器的 55%。通过分析，crypto.rsa 测试程序
执行过程主要在执行蒙哥马利算法，蒙哥马利算法中需要进行多次带进位加
法。LoongArch 64 位指令集没有带进位加法指令，目前是利用 sltu 指令将进位
保存在寄存器中实现的。ARM[32]和 X86[33]指令集架构中均有带进位加法指
令。将 ARM 架构 Java 虚拟机中的蒙哥马利算法改成类似于 LoongArch 的实现
方式，ARM 机器在 crypto.rsa 测试程序的得分和 LoongArch 接近。因此
LoongArch 64 位指令集中若有加法进位指令，LoongArch 64 位 Java 虚拟机的性
能效果会有一定的提升。对于需要频繁用到加法进位指令的加密解密类程序效
果将会更显著。

5.3 下一步工作和研究方向
下一步工作和研究方向将从以下三个方面展开：
第一，同主频 LoongArch 64 位 Java 虚拟机比 MIPS 64 位 Java 虚拟机平均
性能提高了 21.87%，但是与 X86、ARM 架构的 Java 虚拟机在 serial，
scimark.fft.large，crypto.signverify 等测试程序上还有一定的性能差距。接下来
争取分析出这些测试程序在 LoongArch 64 位 Java 虚拟机上的性能瓶颈，缩小
与 X86、ARM 架构的 Java 虚拟机的性能差距，进一步提高 LoongArch 64 位
Java 虚拟机性能。
64
