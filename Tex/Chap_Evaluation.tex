\subsection{实验环境与执行设置}

本文的实验平台基于真实 LoongArch64 目标设备，处理器为龙芯 3A6000，四核八线程，主频 \texttt{2.5\,GHz}，内存为 \texttt{16\,GB}；目标系统为 Android 15，内核版本为 Linux 6.6.46。软件侧以 AOSP 15 源码中的 \texttt{art/} 子项目为研究对象，在完成第 3 章所述平台适配后开展后续验证与性能评测\citep{Loongson3A6000DataBook2023,AospArtAndroid15R1}。

除对不同执行模式的基线比较（详见第~\ref{sec:art-mode-baseline}~节）外，本文关于优化机制的性能结论统一建立在 LoongArch64 64 位 \texttt{debug} ART 与 \texttt{JIT} 模式下。选择这一配置主要出于两方面考量：首先，\texttt{debug} 构建更容易暴露调用约定、异常恢复和慢路径跳转等平台相关问题，有利于在适配收敛过程中建立稳定基线；其次，第 4 章中的正式机制均在相同设置下完成对比，从而保证实验条件的一致性。

DaCapo 的评价指标为执行耗时，单位为 \texttt{msec}，数值越小表示性能越好；SPECjvm2008 的评价指标为 \texttt{ops/m}，数值越大表示吞吐越高。为避免不同指标方向不一致造成误读，本文统一将结果换算为同向的加速比（speedup），再报告相对性能变化。对于吞吐型指标，其定义如式~\ref{eq:speedup-throughput} 所示：
\begin{equation}
    \label{eq:speedup-throughput}
    S_{\text{throughput}} = \frac{M_{\text{scheme}}}{M_{\text{control}}}
\end{equation}
对于时延型指标，其定义如式~\ref{eq:speedup-latency} 所示：
\begin{equation}
    \label{eq:speedup-latency}
    S_{\text{latency}} = \frac{T_{\text{control}}}{T_{\text{scheme}}}
\end{equation}
本文统一按式~\ref{eq:relative-gain} 报告相对性能变化：
\begin{equation}
    \label{eq:relative-gain}
    G = (S - 1)\times 100\%
\end{equation}

\section{基础移植正确性验证}

\subsection{分层验证思路}

本文采用分层验证方式检验执行正确性，包括三个层次。第一，宿主机侧测试尽早发现与平台化改动相关的公共组件回归，例如 DEX 处理、命令行参数解析和编译器基础设施错误。第二，目标机侧 run-test 验证解释执行、编译执行、异常处理、对象访问和调用约定等执行引擎核心语义。第三，libcore 测试进一步覆盖集合框架、输入输出、并发、数学运算、加解密与网络等 Java API 行为。

\subsection{\texorpdfstring{目标机侧 \texttt{run-test} 整体验收}{目标机侧 run-test 整体验收}}

目标机侧 run-test 是验证执行引擎正确性的核心手段。整体验收使用如下命令：
\begin{lstlisting}[language=bash,basicstyle=\ttfamily\small]
art/test.py -r --target --no-prebuild --debug --no-image --64 --all-compiler -j 7
\end{lstlisting}

该命令固定了目标机、\texttt{debug}、\texttt{no-prebuild}、\texttt{no-image} 和 64 位等关键条件，并通过 \texttt{--all-compiler} 展开 \texttt{interp-ac}、\texttt{interpreter}、\texttt{jit}、\texttt{jit-on-first-use}、\texttt{optimizing}、\texttt{speed-profile} 和 \texttt{baseline} 七种 compiler 变体。测试框架会依据 \texttt{knownfailures.json} 中的规则自动跳过不适用配置，最终执行结果如表~\ref{tab:target-run-test-result} 所示。

\subsection{\texorpdfstring{\texttt{libcore} 测试结果}{libcore 测试结果}}

仅依赖 run-test 仍不足以证明 Java 核心类库层面的行为完全正确，本文进一步引入 libcore 测试集，以覆盖集合框架、输入输出、并发、数学运算、加解密与网络等 API 语义。按当前实验归档保留的包级摘要，设备侧已覆盖 libcore 的主要测试包，验证结果以通过为主，少量测试因架构条件限制被自动跳过。

\subsection{优化阶段的最小相关回归}

性能优化阶段不重复执行全量系统回归，而是遵循“最小相关回归优先”原则。每个候选机制在进入基准测试之前，先根据改动所在模块选择直接受影响的目标机测试集合。本文三项正式机制的代表性验证方式如下：
\begin{itemize}
    \item \textbf{自适应基线 JIT 策略。} 重点验证 JIT 队列调度、代码缓存压力测试与启动期状态隔离。
    \item \textbf{批量搬移机制。} 重点验证字符串语义、profile 保存、OSR 和 JIT 路径相关用例。
    \item \textbf{LSX 向量化 lowering 路径。} 重点验证 SIMD 图、数组访问、OSR 与 JIT 路径相关用例。
\end{itemize}

\section{LoongArch 平台下 ART 不同执行模式的基线性能评估}
\label{sec:art-mode-baseline}

在完成正确性验证后，本节统计 \texttt{switch-interpreter}、\texttt{Nterp}、\texttt{JIT} 与 \texttt{JIT-on-first-use} 四种执行模式在代表性基准测试项上的结果，观察移植后 ART 在该平台上的性能阶梯。当前共纳入 24 个基准测试项；在 4 种执行模式下，理论上对应 96 个“测试项$\times$模式”组合，其中 89 个组合具有有效结果，7 个组合缺失。数据汇总时，同一“测试项$\times$模式”仅采用优先级最高来源中的有效结果，不混用不同目录中的多份数据。

为避免不同基准测试集合的指标方向不一致造成误读，本文统一将结果换算为相对 \texttt{switch-interpreter} 的 speedup。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.92\textwidth]{mybenchmark/art-mode-comparison-speedup.pdf}
    \caption{LoongArch 平台下 ART 不同执行模式相对 \texttt{switch-interpreter} 的基线性能比较}
    \label{fig:art-mode-comparison-speedup}
\end{figure}

图~\ref{fig:art-mode-comparison-speedup} 给出了各执行模式相对 \texttt{switch-interpreter} 的分组 speedup。\texttt{Nterp} 相比 \texttt{switch-interpreter} 在当前可比测试项子集上形成了量化差异：\texttt{Startup} 分组为 $8.80\times$，\texttt{Crypto} 分组为 $6.89\times$，说明更高效的解释执行路径能够降低解释器开销。\texttt{JIT} 与 \texttt{JIT-on-first-use} 在部分计算密集型工作负载上继续放大性能优势，例如 \texttt{Compress} 分组分别达到 $769.83\times$ 与 $699.33\times$，独立 \texttt{SciMark} 分组分别达到 $561.92\times$ 与 $497.92\times$，表明热点方法在编译执行后获得了远高于解释执行的吞吐能力。

总体上，移植后的 ART 能够在 LoongArch 平台上呈现清晰的性能阶梯：\texttt{switch-interpreter} 构成基线，\texttt{Nterp} 改进解释执行性能，而 \texttt{JIT} 与 \texttt{JIT-on-first-use} 则在热点工作负载上释放编译执行潜力。

\section{运行时与 JIT 优化策略评估}

为全面评估第 4 章提出的“方法级自适应基线 JIT 进入策略”的实际效果，本节在真实硬件环境中，将其与原生基础版本（Baseline）进行了严格的同口径对照测试。实验不仅选取了代表应用吞吐能力的 SPECjvm2008 \texttt{mpegaudio} 与 DaCapo \texttt{pmd} 工作负载，还重点针对机制设计的靶心——启动期（Startup）负载进行了下钻分析。

\subsection{与完整 SIMD 覆盖候选版的边界比较}

对于多工作负载的整体比较，本文采用几何平均 speedup 作为统一统计量，其定义如式~\ref{eq:geomean-speedup} 所示：
\begin{equation}
    \label{eq:geomean-speedup}
    \operatorname{GM}(S_1,\ldots,S_n)=\left(\prod_{i=1}^{n} S_i\right)^{1/n}
\end{equation}

\section{本章小结}

本章给出了实验环境、正确性验证、正式对比与扩展分析的结果。移植工作通过 run-test 与 libcore 验证建立了正确性基础。三类正式机制在统一实验条件下呈现出差异化的性能变化特征：自适应基线 JIT 策略在启动期短生命周期负载上取得 \texttt{2.01\%} 至 \texttt{34.29\%} 的相对基线性能提升，并通过资源否决（Veto）机制应对突发的高压负载；批量搬移机制作为定向的底层微优化，在 \texttt{pmd} 与 \texttt{mpegaudio} 上分别对应 \texttt{0.86\%} 与 \texttt{0.71\%} 的相对性能变化；LSX 向量化 lowering 路径则在规则浮点数值内核 \texttt{lu.small} 上取得 \texttt{44.40\%} 的吞吐量提升。扩展评估中的多机制叠加冲突进一步证实，LoongArch 平台上的 ART 优化必须围绕具体的微观工作负载主路径展开，不能简单地叠加优化策略。
