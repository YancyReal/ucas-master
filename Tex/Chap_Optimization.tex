\chapter{面向 LoongArch 架构的 ART 性能优化}\label{chap:optimization}

\section{优化问题建模与总体策略}

完成第 3 章的基础执行框架移植之后，LoongArch 平台上的 ART 已具备解释执行、JIT 编译、跨语言调用和运行时支撑能力。此时，后续工作的重点不再是基础功能补齐，而是围绕正式工作负载的主导瓶颈，识别稳定命中的关键路径，并据此设计具有明确作用点和实现边界的优化机制。

在 LoongArch 平台的 ART 运行环境中，局部热点并不直接等价于研究问题。火焰图（flamegraph）、\texttt{report\_symbol.txt} 与局部 profile 可以揭示时间开销的集中位置，但这些观察结果仍需结合工作负载生命周期、调用路径稳定性以及实现可控性进一步分析，才能收缩为可验证的优化对象。基于这一点，本文将优化问题统一建模为“成本类型、工作负载特征与可观测证据”的交集，并据此组织后续优化设计。

围绕 LoongArch 平台 ART 的典型运行行为，本文将优化对象归纳为四类成本问题，如表~\ref{tab:problem-modeling-axes} 所示。它们分别对应短生命周期工作负载中的 JIT 进入时机问题、运行时稳态阶段的热路径数据搬移成本、启动期 DEX 校验链上的固定成本，以及规则浮点循环在后端向量化支持上的能力缺口。其中，前两类问题与启动期问题对应本章后续的具体机制设计，规则浮点循环的向量化支持问题将在第 4.4 节展开。

表~\ref{tab:problem-modeling-axes} 所列四类问题对应不同的系统成本来源。JIT 进入时机问题关注短生命周期工作负载从解释执行进入 baseline JIT 的首层介入窗口；运行时热路径问题关注小长度、高频次的数据搬移成本；启动期问题关注 DEX 校验主链中的查询、校验与元数据解码开销；向量化支持问题关注规则浮点循环已形成向量 IR 后，后端能否将其稳定 lowering 为 LSX 指令。

围绕上述问题，本文采用三项原则约束后续机制设计。第一，热点必须落实为工作负载主要路径，局部符号热度本身不足以构成优化对象。第二，优化机制必须具备明确作用点、实现边界和失效条件，使性能提升能够获得稳定解释。第三，不同机制之间应保持问题定义、实现边界与适用场景一致，使后续评估能够围绕同一成本模型展开。

\section{短生命周期工作负载中的 JIT 进入时机优化}

\subsection{短生命周期工作负载的编译窗口分析}

本节讨论短生命周期工作负载中的 JIT 进入时机问题。在 LoongArch64 \texttt{debug} JIT 环境中，\texttt{pmd} 一类短生命周期工作负载的关键约束来自方法热度的累积窗口。ART 的分层 JIT 至少包含两级关键阈值：第一层阈值 \texttt{warmup\_threshold} 决定方法何时进入 baseline JIT，第二层阈值 \texttt{optimize\_threshold} 决定方法何时进一步进入 optimizing 编译。当 benchmark 生命周期较短、热度累积窗口有限时，若第一层阈值偏高，许多热点方法将在 benchmark 结束前持续停留于解释执行状态\citep{Arnold2005,ArtJitCompiler2024,Perez2012HybridJIT,Xu2018ShareJIT}。

从时间开销构成看，这类工作负载的总执行时间大致可以分为两个阶段：第一阶段是热点方法在解释器中累积热度并等待首次编译；第二阶段是方法进入编译态后的执行时间。只要第一阶段占比过大，后续是否进一步进入 optimizing 编译对总执行时间的影响就会明显减弱，因为很多方法甚至来不及跨过 baseline JIT 门槛。基于这一观察，本文将问题聚焦于“首次脱离解释器”的控制流相变点，即 baseline JIT 的进入窗口。

进一步从分层编译模型看，\texttt{warmup\_threshold} 与 \texttt{optimize\_threshold} 对应两种不同性质的决策。前者回答“一个方法是否值得从解释执行切换到本地代码执行”，其收益主要来自降低解释器分派、栈帧解释和字节码逐条执行的固定开销；后者回答“一个已经具备足够运行期信息的方法是否值得投入更高编译成本”，其收益主要来自更充分的内联、类型专门化、寄存器分配和循环优化。二者虽然都属于 JIT 策略参数，但作用时间点和成本结构并不相同。若将二者混为同一类阈值调优，容易把首层编译介入不足的问题误判为高层优化不充分的问题。

对短生命周期负载而言，这一区分尤为关键。此类负载的执行时间窗口有限，方法热度分布又可能在短时间内集中爆发。若默认首层阈值使热点方法迟迟不能进入 baseline JIT，则系统主要时间仍消耗在解释执行阶段；此时即使下调 \texttt{optimize\_threshold}，也只能影响已经跨过第一层门槛并继续保持热度的方法，无法覆盖尚未脱离解释器的大量短期热点。换言之，第二层 optimizing 编译的收益前提，是方法已经及时进入了第一层本地代码执行路径。

这也是本文不将优化对象设定为“整体提高 JIT 激进程度”的原因。过早触发 optimizing 编译会放大编译线程、Code Cache 和调试元数据压力，并可能在短生命周期场景中因编译成本难以摊销而抵消收益。相比之下，baseline JIT 的目标更接近本文观察到的主导矛盾：以较低编译成本尽快越过解释器边界，让真正具备快速热度推进特征的方法获得本地代码执行机会。因此，本节后续机制仅围绕首层编译窗口设计受限提前触发条件，而不改变第二层 optimizing 编译的基本语义。

\subsection{基于方法特征与系统状态的自适应基线 JIT 提前触发机制}

针对上一小节所述这一问题，一种直接思路是全局下调首层编译阈值；但这种做法会同时放宽所有方法的进入条件，容易使大量优化价值有限的方法过早进入编译队列，从而带来代码缓存膨胀和编译资源竞争。

基于这一约束，本文不采用统一下调阈值的全局方案，而是在保留默认 \texttt{warmup\_threshold} 语义不变的前提下，引入一个受限的提前触发窗口。其基本思想是：仅当方法同时表现出短生命周期热点的局部特征，且运行时资源状态允许时，才允许该方法在达到默认阈值之前提前进入 baseline JIT；其余情况仍沿用原有触发路径。这样，机制的作用点仍然限定在“首次脱离解释器”的首层编译介入窗口，而不是改变整套分层 JIT 的通用阈值语义。

按此设计，首层编译触发过程可划分为三个区间：
\begin{enumerate}
    \item \textbf{常规累计区}：方法热度仍处于早期累计阶段，继续解释执行。
    \item \textbf{受限提前触发区}：方法尚未达到默认 \texttt{warmup\_threshold}，但已满足提前触发所需的方法级条件，且系统状态允许，因此提前进入编译队列。
    \item \textbf{标准触发区}：方法热度达到默认 \texttt{warmup\_threshold}，按原有语义进入 baseline JIT。
\end{enumerate}

为避免提前触发退化为新的全局性放宽，本文将判定条件分解为“方法级资格条件”和“系统状态否决条件”两部分。只有当二者同时满足时，方法才允许在默认阈值之前进入 baseline JIT。

\textbf{1. 方法级资格条件}：机制仅在满足以下条件时激活提前触发窗口：
\begin{itemize}
    \item \textbf{运行早期约束}：机制仅在进程尚处于运行早期阶段（\texttt{!GetStartupCompleted()}）时生效，以限制其作用范围，并使其主要服务于短生命周期工作负载中最重要的首层编译介入窗口。
    \item \textbf{小方法体约束}：仅允许指令单元较小（\texttt{code\_units $\le$ 128}）的方法提前进入，避免大体积方法过早编译带来额外开销。
    \item \textbf{热度快速推进检测}：将原始 \texttt{warmup\_threshold} 划分为若干离散阶段（如 1/8、1/4、1/2 处）。若方法在较短采样周期（\texttt{sample\_epoch}）内连续跨越这些阶段，则将其视为热度推进较快的方法。
    \item \textbf{调用边界代理信号}：引入 \texttt{invoke\_entries $\ge$ 3} 作为轻量级运行时代理信号，用于辅助刻画方法的调用活跃度。
\end{itemize}

\textbf{2. 系统状态否决条件}：即使方法满足上述资格条件，若系统处于高压状态，机制仍拒绝其提前进入编译队列：
\begin{itemize}
    \item \textbf{编译队列状态约束}：要求当前编译线程池无积压任务（\texttt{pending\_compilations == 0}）。
    \item \textbf{内存与代码缓存状态约束}：要求 Profile 信息能够正常分配，且 Code Cache 使用率处于安全区间（如低于 75\%）。
\end{itemize}

上述联合判定逻辑的核心形式如算法~\ref{alg:adaptive-warmup-rule} 所示。

\begin{algorithm}[htbp]
    \small
    \caption{方法级自适应基线 JIT 提前触发判定机制}
    \label{alg:adaptive-warmup-rule}
    \begin{algorithmic}[1]
        \State \textbf{Input:} \textit{method}, \textit{thread}, \textit{runtime\_state}
        \State \textbf{Output:} boolean \textit{should\_trigger\_early}
        
        \State // 1. 运行时阶段约束
        \If{\textit{runtime\_state}.\texttt{GetStartupCompleted()} is true}
            \State \textbf{return} false
        \EndIf
        
        \State // 2. 方法级资格条件
        \If{\textit{method}.\texttt{GetCodeUnits()} $> 128$}
            \State \textbf{return} false \Comment{过滤大方法}
        \EndIf
        \If{\textit{method}.\texttt{GetInvokeEntries()} $< 3$}
            \State \textbf{return} false \Comment{调用活跃度不足}
        \EndIf
        \If{\textbf{not} \texttt{IsHeatProgressionFast}(\textit{method})}
            \State \textbf{return} false \Comment{热度累积不具备快速推进特征}
        \EndIf
        
        \State // 3. 系统状态否决条件
        \If{\textit{runtime\_state}.\texttt{GetPendingCompilations()} $> 0$}
            \State \textbf{return} false \Comment{编译队列存在积压}
        \EndIf
        \If{\textit{runtime\_state}.\texttt{GetCodeCacheUsage()} $> 0.75$}
            \State \textbf{return} false \Comment{Code Cache 压力过大}
        \EndIf
        \If{\textbf{not} \textit{runtime\_state}.\texttt{CanAllocateProfilingInfo()}}
            \State \textbf{return} false \Comment{Profile 内存受限}
        \EndIf
        
        \State \textbf{return} true
    \end{algorithmic}
\end{algorithm}

该机制的实现边界也应明确说明。首先，它并不改变默认 \texttt{warmup\_threshold} 在一般情形下的原有语义，只在默认阈值之前增加一个受限的提前触发窗口。其次，它仅服务于短生命周期工作负载中“首层编译是否及时介入”这一问题，并不试图同时解决 optimizing 编译、长期稳态编译吞吐或更广义的运行时调度问题。最后，当方法不满足资格条件，或者系统状态触发否决条件时，方法统一沿原有路径继续累计热度并等待原始阈值触发。

\section{运行时与启动期关键路径优化}

本节进一步讨论 ART 运行过程中不直接属于 JIT 进入时机或后端向量化能力的问题。与第 4.2 节关注“热点方法何时进入 baseline JIT”不同，本节关注已经落在运行时关键路径上的固定成本：一类出现在稳态执行阶段，表现为字符串构造、替换与拼接路径中的高频小规模数据搬移；另一类出现在启动期阶段，表现为 DEX 校验链中的容器查询、字符串校验与元数据解码开销。二者所处阶段不同，但共同特点是主路径清晰、局部机制可控，并且能够通过有限边界内的结构调整降低固定开销。

因此，本节按照“运行时稳态路径”和“启动期阶段路径”分别展开。第 4.3.1 节讨论字符串热路径中的 8 路批量搬移机制，第 4.3.2 节讨论 DEX 校验流水线的阶段化优化策略。

\subsection{运行时稳态：面向字符串热路径的 8 路批量搬移机制}

运行时稳态路径的核心问题，是高频但单次规模较小的数据搬移难以摊薄循环框架与边界判断成本。本小节首先从 \texttt{pmd} 等工作负载中反复出现的字符串处理路径出发，界定该类成本的主路径来源；随后再比较不同运行时热路径候选方向，并将正式机制收缩到字符串热路径的 8 路批量搬移实现。

\subsubsection{问题界定与主路径识别}

本节讨论运行时字符串热路径中的高频搬移成本。对 \texttt{pmd} 的 flamegraph、profile 与运行时实现路径的持续分析表明，字符串替换、字符串拼接、UTF-16 构造以及 \texttt{StringBuilderAppend} 相关路径会稳定出现，其代表性入口包括 \texttt{String::DoReplace()}、\texttt{String::DoConcat()} 与 \texttt{String::AllocFromUtf16()}。这些路径往往长度不长但调用频繁，复制逻辑本身较简单，因此循环控制、索引换算和逐元素分支的固定开销难以被单次工作量摊薄\citep{Haubl2008OptimizedStrings,Haubl2010CompactStrings}。

\subsubsection{机制收缩与实现边界}

运行时热路径类候选方向的共同来源，是用户态运行时内部高频复制、校验或辅助逻辑。按作用对象划分，这类方向大致可以归为三种技术路线：一类围绕字符串或 Unicode 处理路径进行专用展开与局部向量化，另一类尝试对通用复制入口进行低层接线或替换，还有一类围绕特定启动链进行结构性重排\citep{Haubl2008OptimizedStrings,Haubl2010CompactStrings,Cameron2008SIMDUTF,Lemire2022UnicodeSIMD}。

表~\ref{tab:runtime-candidates} 给出了运行时热路径类候选方向的技术评估。原始数组批量搬运、\texttt{memcpy} 接线与 CRC32 JNI 快路径要么入口过宽，要么热点占比过低，与正式工作负载之间缺少稳定机制联系。相较之下，字符串热路径的 8 路批量搬移机制它既能稳定命中工作负载主路径，又具备清楚的实现边界；该机制主要围绕运行时字符串分配、构造与替换路径展开，通过在已知字符串语义、压缩判定已完成的前提下，将原有逐元素复制逻辑改写为显式展开的批量搬移结构。其核心在于压缩正式工作负载主路径中的循环框架成本。该机制需严格处理尾部边界条件。为防止小长度（\texttt{length < 8}）下的无符号下溢及越界访问，机制设计被划分为主循环的 8 路展开与尾部逐元素拷贝两部分：如算法~\ref{alg:scheme2-bulk-copy-helper} 所示，仅在 \texttt{i + 8 <= length} 时进入展开循环，其余元素统一走尾部路径，从而保持短字符串场景下的语义正确性与边界安全。

\begin{algorithm}[htbp]
    \small
    \caption{字符串热路径 8 路批量搬移机制的复制内核}
    \label{alg:scheme2-bulk-copy-helper}
    \begin{algorithmic}[1]
        \State \textbf{Input:} destination byte array $dst8$, source UTF-16 array $src16$, copy length $length$
        \State \textbf{Output:} byte array $dst8$ after bulk copy
        \State $i \gets 0$
        \While{$i + 8 \leq length$}
            \For{$lane \gets 0$ \textbf{to} $7$}
                \State $dst8[i + lane] \gets \texttt{uint8\_t}(src16[i + lane])$
            \EndFor
            \State $i \gets i + 8$
        \EndWhile
        \While{$i < length$}
            \State $dst8[i] \gets \texttt{uint8\_t}(src16[i])$
            \State $i \gets i + 1$
        \EndWhile
    \end{algorithmic}
\end{algorithm}

\subsection{启动期阶段：DEX 校验流水线的优化策略}

与运行时稳态阶段不同，启动期阶段的主要矛盾不是某一类操作在长时间执行中的反复累积，而是 DEX 校验主链在应用启动窗口内形成的固定成本。本小节因此先识别 \texttt{DexFileVerifier} 相关路径在启动期快照中的主导开销，再按照校验链上的不同作用点组织阶段化优化，使容器查询、字符串校验和元数据解码等成本分别对应明确的实现边界。

\subsubsection{问题界定与主路径识别}

\texttt{DexFileVerifier} 相关工作对应的是启动期校验主链，而非稳态执行阶段的局部热点。在启动期校验快照（\texttt{Snapshot-C}）中，\texttt{startup.helloworld} 的对照版本 flamegraph 表明，\texttt{OffsetToPtr}、\texttt{FindIndexImpl}、\texttt{ElementForIndex}、\texttt{PtrToOffset} 与 \texttt{CheckIntraDebugInfoItem} 等 verifier、container 与字符串校验相关路径在启动时间中占有稳定比例。相比之下，这类热点在 \texttt{scimark.lu.small} 等稳态数值工作负载中占比显著更低。因此，本文将 \texttt{startup.helloworld} 视为该问题的代表工作负载，并使用稳态数值工作负载作为对照，以区分启动期优化与稳态优化的成本边界。

\subsubsection{机制收缩与阶段边界}

围绕启动期 DEX 校验链，潜在的优化方向可以同时覆盖容器访问、字符串校验、元数据解码乃至更大范围的校验器重构。但从正式工作负载的主路径出发，本文不采用对 verifier 的整体重写，而是沿启动期主链将主要固定成本拆解为若干具有明确作用点的阶段性问题，并据此组织局部机制。启动期 DEX 校验链的优化沿主热点路径拆解为四个阶段，如表~\ref{tab:dexverifier-phases} 所示。这样组织的目的，是将 container 查询、字符串校验与元数据解码等不同成本分离出来，使每一阶段都对应明确的作用点和实现边界。

    \caption{DexFileVerifier 阶段链的关键钩子算法}
    \label{alg:dexverifier-phase-chain-hooks}
    \begin{algorithmic}[1]
        \State \textbf{Input:} map list $map\_list$, verifier metadata structures
        \State \textbf{Output:} section verification result and staged helper behavior
        \State \textbf{Procedure:} VerifyDexSectionChain($map\_list$)
        \State Reserve capacity for $offset\_to\_type\_map$
        \ForAll{$item \in map\_list$}
            \State Check padding at $(item.offset, item.type)$
            \State Dispatch section check by $item.type$
        \EndFor

\section{规则浮点循环的 LSX 向量化支持}

\subsection{规则浮点循环的向量化问题定义}

本节关注的问题来自编译器后端能力：当 ART 前端已经识别出可向量化循环时，LoongArch64 后端是否具备将向量 IR 稳定转化为向量机器码的最小 LSX lowering 路径。以 \texttt{scimark.lu.small} 为代表的规则浮点数值内核通常具备如下特征：循环可计数、数组访问为连续单位步长、存在循环不变量广播值，以及以加减乘为主的稳定算子组合。对于这类问题，性能瓶颈主要来自向量化机会能否真正命中目标 ISA。

\begin{table}[htbp]
    \centering
    \small
    \caption{规则浮点循环进入最小 LSX 路径分析的结构条件}
    \label{tab:simd-kernel-features}

        \toprule
        \textbf{条件} & \textbf{对 LSX 最小路径的含义} \\
        \midrule
        连续单位步长数组访问 & 便于直接映射到 \texttt{VecLoad/VecStore}，避免复杂 gather/scatter 需求 \\
        循环不变量广播值 & 需要后端支持标量到向量的复制，即 \texttt{VecReplicateScalar} \\
        加减乘为主的稳定算子组合 & 只需最小可用的浮点 \texttt{VecAdd/VecSub/VecMul} 即可解释主要性能提升 \\

        不依赖复杂 idiom 与完整后端覆盖 & 使分析能够先证明“最小可用路径成立”，而非过早扩展到完整 SIMD 后端 \\

\end{table}

表~\ref{tab:simd-kernel-features} 给出了规则浮点循环进入最小 LSX 路径分析的结构条件。这些条件共同决定了问题的分析范围：本文只关注规则浮点循环所需的数据类型、算子组合、向量宽度与 lowering 链路，而不扩展到更复杂的 gather/scatter、通用整数 SIMD 或完整 SIMD 后端覆盖。

\subsection{LoongArch64 最小可用 LSX 浮点 SIMD 路径设计}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=1.00\textwidth]{optimization/scheme3-vectorization-boundary.pdf}
    \caption{最小可用 LSX 浮点 SIMD 路径的能力边界}
    \label{fig:scheme3-vectorization-boundary}
\end{figure}

图~\ref{fig:scheme3-vectorization-boundary} 展示了 LSX 向量化 lowering 路径的能力边界。此处“最小可用”对应两个限定条件：其一，正式论证所依赖的是规则浮点循环所需的最小能力集合，只覆盖正文分析所需的数据类型、算子、寄存器宽度和 lowering 路径；其二，相关路径必须已经通过最小回归验证，并能够稳定生成目标向量代码。

在实现上，本文将最小路径限定为如下能力集合：面向 \texttt{float32/float64} 的 128-bit 向量路径（其中 \texttt{float32} 为 4 lane，\texttt{float64} 为 2 lane）；支持 \texttt{VecReplicateScalar}、\texttt{VecLoad}、\texttt{VecStore}、\texttt{VecAdd}、\texttt{VecSub}、\texttt{VecMul} 等核心算子；并对 \texttt{int32 -> float32} 与 \texttt{int64 -> float64} 保留受限的 \texttt{VecCnv}，用于支撑特定循环形态。

\begin{algorithm}[htbp]
    \small
    \caption{LSX 向量化 lowering 路径的保守启用算法}
    \label{alg:lsx-enable-rule}
    \begin{algorithmic}[1]
        \State \textbf{Input:} target ISA, loop shape, packed type, operator set, lowering capability
        \State \textbf{Output:} \textit{MinimalLSXPath} or \textit{ScalarPath}
        \If{target ISA is not LoongArch64}
            \State \textbf{return} \textit{ScalarPath}
        \EndIf
        \If{loop is not countable \textbf{or} loop is not unit-stride}
            \State \textbf{return} \textit{ScalarPath}
        \EndIf
        \If{$packed\_type \notin \{float32, float64\}$}
            \State \textbf{return} \textit{ScalarPath}
        \EndIf
        \If{$op\_set \not\subseteq \{$ReplicateScalar, Load, Store, Add, Sub, Mul, Cnv$\}$}
            \State \textbf{return} \textit{ScalarPath}
        \EndIf
        \If{vector length does not match 128-bit LSX for $packed\_type$}
            \State \textbf{return} \textit{ScalarPath}
        \EndIf
        \If{required IR nodes cannot all be lowered to LSX}
            \State \textbf{return} \textit{ScalarPath}
        \EndIf
        \State \textbf{return} \textit{MinimalLSXPath}
    \end{algorithmic}
\end{algorithm}

算法~\ref{alg:lsx-enable-rule} 给出了该路径的启用规则：只有当循环形态、数据类型、向量长度和 lowering 能力同时满足条件时，才进入 LSX 向量路径；其余情形统一回退到既有标量路径。

\section{本章小结}

本章围绕 JIT 进入时机、运行时稳态热路径、启动期校验链和后端向量化支持四类主导问题，给出了 LoongArch 平台 ART 的优化问题建模、机制设计与实现边界。自适应基线 JIT 提前触发机制聚焦短生命周期工作负载中首层编译的介入窗口，字符串热路径的 8 路批量搬移机制聚焦运行时小长度高频复制问题，DEX 校验流水线的阶段性精简聚焦启动期主链上的固定成本压缩，LSX 向量化 lowering 路径则聚焦规则浮点循环的最小后端能力补齐。对应机制的实验环境、正确性验证与性能结果将在第 5 章统一评估。
