\chapter{LoongArch平台ART执行能力构建}\label{chap:porting}

\section{适配目标、范围与设计原则}

相较于普通用户态程序，ART 的平台适配不是若干体系结构相关文件的局部迁移，而是执行引擎能力的系统性
构建过程\citep{AndroidRuntime2024,ArtJitCompiler2024,LoongArchISA2023,
LoongArchELFABI2025}。原因在于，解释器、JIT 编译器、JNI 桥接与运行时入口点之间存在紧密耦合；
任何一个子系统缺失，都可能使 Java 方法调用链、异常恢复链或 Java/native 边界调用链无法真正打通。
因此，本文将 LoongArch 平台上的 ART 适配目标界定为一个“四能力单元”问题：解释器与 Nterp、
JIT 编译器后端、JNI 编译器与运行时入口点，以及标准库与 Intrinsic 的基础能力。

围绕这一目标，本文遵循三条设计原则。第一，先建立最小执行路径，再逐步补齐高性能路径，即以
C++ 解释器建立语义基线，再扩展到 Nterp、JIT 与 JNI。第二，先统一底层发射与调用约定，再补齐上层
执行语义，使寄存器约束、标签跳转、链接修补和返回值通道在不同组件之间保持一致。第三，任何新增能力都
必须对应可验证接口，即它不仅要“能够运行”，还要能够被第 4 章的正确性验证链和后续性能评测体系接住。

图~\ref{fig:art-porting-overview} 给出了 AOSP 15 中与 ART 执行引擎相关的主要结构以及本文直接适配
或补齐的重点模块。LoongArch 平台适配并不是单独补齐某个代码生成器文件，而是要让编译器侧、运行时侧
与公共支撑库之间形成统一接口链路。

需要特别说明的是，汇编器与链接修补机制在本文中并不被单独视为“最终能力”，而是四个能力单元共享的
底层发射支撑。它的价值不在于逐类枚举所有指令接口，而在于为解释器、JIT 与运行时桩代码提供统一的
机器描述、标签跳转、字面量组织与回填能力。只有这一基础被统一之后，Nterp 派发表、JIT SlowPath、
JNI 桥接和 quick entrypoints 才能共享同一套调用约定与控制流组织方式\citep{LoongArchISA2023,
LoongArchToolchain2025}。

\section{解释器与 Nterp 适配}

C++ 解释器是本文建立 LoongArch 平台最小可运行路径的起点。与 Nterp 和 JIT 相比，它对平台特定
汇编能力依赖最少，因此能够尽早暴露方法调用、参数传递、ShadowFrame 布局以及异常传播中的基础问题。
适配工作的关键，不是让某个简单样例“偶然跑通”，而是让 \texttt{ArtMethod::Invoke()} 进入解释执行时，
\texttt{Thread*}、\texttt{ArtMethod*}、参数区和返回值通道都能与 LoongArch64 ABI 保持一致，
并保证 DEX PC、调用现场与异常状态可被稳定保存与恢复。

在 C++ 解释器具备稳定语义后，本文继续建立 LoongArch64 下的 Nterp 汇编解释器。Nterp 的核心不是
重写一遍解释器逻辑，而是通过固定寄存器协议、派发表和汇编处理块，把热点解释执行路径从共享
\texttt{switch-case} 分派转换为更直接的控制流组织\citep{Ertl2003,ArtJitCompiler2024}。
为此，本文首先确定解释器帧指针、当前 DEX PC、派发表基址等关键寄存器的固定分工，再补齐入口、返回、
类初始化和 helper 调用等骨架路径，使 Nterp 可以在 LoongArch64 上形成可扩展的汇编解释执行框架。

Nterp 的真正难点在于字节码处理逻辑的逐类补齐与平台问题修复。本文按照“基础指令
$\rightarrow$ 对象与数组语义 $\rightarrow$ 各类 invoke 变体”的顺序推进，并在这一过程中集中解决了
三类代表性问题：Nterp 与调用桩之间的栈帧衔接问题、LoongArch64 浮点 NaN 分类差异问题，以及 JIT
与 Nterp 混合执行时的对象状态一致性问题。经过上述修复，LoongArch 平台不仅具备了平台无关的解释执行
能力，也具备了与主流架构接近的高性能解释执行通路。

\section{JIT 编译器后端与 JNI 编译器适配}

如果说解释器适配解决的是“代码尚未编译时如何执行”的问题，那么 JIT 后端适配解决的就是“热点代码如何
生成 LoongArch64 机器码”的问题。ART 的 Optimizing Compiler 以前端构建的 HIR 为核心中间表示，
平台后端则负责把寄存器分配、调用约定和目标指令发射连接起来。因此，本文首先补齐了
\texttt{CodeGeneratorLOONGARCH64}、调用约定访问器、栈帧管理与并行移动等基础设施，使 LoongArch64
后端能够接入 ART 既有的寄存器分配与代码布局流程。

在这一基础上，本文进一步补齐了从基础算术、分支、返回到对象、数组、字段访问与多类 invoke 节点的
HIR 支持，并配套实现了空指针、越界、类初始化和异常处理等 SlowPath 组织方式。这里真正重要的不是
“支持了多少节点”，而是 LoongArch64 后端已经能够在主路径代码生成、慢路径回退、链接修补和 OSR/
deoptimization 协同之间保持一致行为\citep{Fink2003,Lameed2013}。这意味着 LoongArch64 JIT
后端不再是静态指令发射器，而是能够参与 ART 的分层执行生态。

JNI 编译器适配则解决了 Java 与 native 之间的调用链打通问题。对于新架构平台而言，即使解释器与 JIT
都已经可用，若缺失 JNI 调用约定描述、宏汇编器骨架和线程状态切换路径，Java 方法仍无法稳定调用
native 代码。为此，本文补齐了 LoongArch64 下 Java 参数、返回值、\texttt{JNIEnv*} 与隐藏参数的
寄存器/栈映射，实现了 JNI 宏汇编器、JNI 帧建立与恢复、线程状态从 Runnable 到 Native 的切换逻辑，
并以普通 JNI 调用路径为优先收敛目标，使跨语言调用链能够在 LoongArch 平台上稳定闭合。

\section{运行时入口点与快速路径补齐}

解释器、JIT 与 JNI 能否协同工作，最终取决于它们是否共享同一套运行时入口点。对象分配、字段访问、
类型检查、类解析、异常抛出和方法调用等高频语义，最终都要通过 \texttt{art\_quick\_*} 入口点或
相关 trampoline 落到运行时实现上。因此，运行时快速路径的补齐并非附属工作，而是执行能力构建中的第四个
关键环节。

图~\ref{fig:art-runtime-cooperation} 概括了三类主要执行路径与运行时服务之间的关系：C++ 解释器更常
直接调用运行时辅助函数，而 Nterp 与编译代码更依赖 quick entrypoints 和 trampoline 将对象分配、
类解析、异常处理和 JNI 支撑接入主路径。围绕这一协同关系，本文逐步接入了对象分配入口点、
\texttt{CheckInstanceOf} 相关入口、快速字段访问入口、类解析入口、deopt 入口、接口冲突表
trampoline 以及若干数学与字符串辅助入口，使 LoongArch 平台上的不同执行模式能够共享同一运行时支撑层。

在运行时入口点基本闭合之后，本文继续补齐标准库与 Intrinsic 的基础能力，包括 Memory peek/poke、
\texttt{Float}/\texttt{Double} 相关路径、整型与浮点最值计算以及 \texttt{Math.fma} 等高频语义。
这一阶段的目标不是立即榨取极致性能，而是确保热点标准库语义在 LoongArch 平台上具备正确、稳定且可
回归的机器级实现。换言之，Intrinsic 在本章中的角色首先是“执行能力完善”，而不是“正文主结果”；
这也为后文将相关补充材料放入附录、而不与正文主结论混算奠定了边界。

\section{可运行执行环境的形成与验证接口}

经过前述四个能力单元的补齐，LoongArch 平台上的 ART 从“只有零散机器描述和部分汇编能力”逐步演化为
一个可运行、可编译、可跨语言调用、可验证的执行环境。其阶段性结果并不体现在某一个局部优化点上，
而体现在执行链是否已经完整建立：C++ 解释器提供语义基线，Nterp 提供高效解释执行路径，JIT 后端提供
编译执行能力，JNI 与运行时入口点打通 Java/native 边界，而标准库与 Intrinsic 则补齐高频语义的
基础支撑。

更重要的是，这些能力并非停留在“能跑一些样例”的层面，而是向第 4 章暴露了清晰的验证接口。其一，
完整编译与部署链可以稳定产生 LoongArch64 目标产物；其二，目标机 \texttt{run-test} 与
\texttt{libcore} 测试能够覆盖解释执行、编译执行、异常处理、对象访问和 Java API 行为；其三，
基准测试入口能够在统一 baseline 下采集分数、日志、热点统计与 flamegraph。也就是说，第 4 章的
验证体系并不是额外附加的实验包装，而是本章执行能力构建自然暴露出的证据接口。

从研究边界看，本文将从初始移植起点到稳定 baseline 版本这一提交区间视为“执行能力构建阶段”的主体成果。
这一阶段工作的核心价值，不在于单个 patch，而在于系统性补齐了 LoongArch 平台上 ART 执行引擎所需的
关键构件，使随后展开的正确性验证、方案筛选与性能优化建立在完整、可验证的工程基础之上。

\section{本章小结}

本章将 LoongArch 平台上的 ART 适配重写为一个执行能力构建问题，而不是模块清单问题。其核心结论是：
解释器与 Nterp 解决最小与高效解释执行路径，JIT 编译器后端与 JNI 编译器解决编译执行与跨语言调用链，
运行时入口点与标准库基础能力负责把不同执行模式接到同一运行时支撑层上。只有这四个能力单元共同成立，
LoongArch 平台上的 ART 才能从“局部可运行”演进为“系统可验证、可研究、可优化”的完整运行环境。
下一章将在此基础上继续建立正文证据链，回答哪些数据可以进入论文主结论，以及这些数据为什么可信。
