\chapter{主结论与综合讨论：LoongArch64 最小可用 LSX 浮点 SIMD 路径}\label{chap:simd}

\section{规则浮点数值内核的向量化问题定义}

在第 5 章完成问题筛选与局部案例讨论后，本章转向全文主结论。本章关注的问题源于编译器后端能力：当 ART 前端能够识别可向量化循环时，LoongArch64 后端是否具备将向量 IR 转化为向量机器码的最小 LSX lowering 路径。为与第 5 章保持一致，本文继续采用“方向性受益、局部受益、稳定且幅度较大的受益”三层结论强度口径。该方向在统一实验链下同时满足收益幅度、重复测量稳定性与机制可解释性，因而作为全文主结论。它也最能体现平台适配从“可运行”走向“可高效运行”的关键跃迁。

以 \texttt{scimark.lu.small} 为代表的规则浮点数值内核，通常具备如下特征：循环可计数、数组访问为连续单位步长、存在循环不变量广播值，以及以加减乘为主的稳定算子组合。对于这类内核，性能瓶颈不再是解释器驻留或运行时固定成本，而是向量化机会能否真正落实到目标 ISA。如果前端只能构造向量 IR，却无法在 LoongArch64 后端完成 lowering，那么这些循环本质上仍然停留在标量执行路径。已有 Java 向量化研究同样表明，收益是否能够兑现，取决于“可识别、可合法化、可落地”这三层能力是否同时成立 \citep{Nie2010VectorizationJava}；正文方案三恰好聚焦于此前最薄弱的最后一层。

表~\ref{tab:simd-kernel-features} 解释了本章将问题收敛于“最小可用 LSX 浮点 SIMD 路径”的原因。\texttt{lu.small} 内层循环最关键的计算模式可以概括为“标量广播值乘以一段连续数组，再减到另一段连续数组”。其对向量化的要求并非无限制的 ISA 覆盖，而是一组需同时满足的基础能力：广播、连续 load/store、浮点加减乘及必要的类型转换。补齐这组最小能力，即可将停留在标量流的热点循环转化为真正的 LSX 向量流。

\section{LoongArch64 最小可用 LSX 浮点 SIMD 路径}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=1.00\textwidth]{optimization/scheme3-vectorization-boundary.pdf}
    \caption{最小可用 LSX 浮点 SIMD 路径的能力边界}
    \label{fig:scheme3-vectorization-boundary}
\end{figure}

图~\ref{fig:scheme3-vectorization-boundary} 展示了方案三的能力边界。此处的“最小可用”意味着本文仅回答一个受限问题：LoongArch64 是否具备使规则浮点循环稳定转化为 LSX 向量机器码的最小能力集。为避免“最小”和“可用”在语义上继续游移，本文将其形式化限定为两个条件：其一，“最小”指正文主结论真正依赖的最小能力集合，只覆盖规则浮点循环所需的数据类型、算子、寄存器宽度和 lowering 路径；其二，“可用”指该路径已经通过最小回归验证、能够稳定生成目标向量代码，并在统一实验链中获得可重复的性能提升。此定义排除了“一次性完成完整 SIMD 后端”或“使所有数值工作负载自动受益”等宽泛论述。

在实现上，本文将最小路径限定为特定能力集合。具体而言，包括面向 \texttt{float32/float64} 的 128-bit 向量路径（其中 \texttt{float32} 为 4 lane，\texttt{float64} 为 2 lane）；支持 \texttt{VecReplicateScalar}、\texttt{VecLoad}、\texttt{VecStore}、\texttt{VecAdd}、\texttt{VecSub}、\texttt{VecMul} 等核心算子；并对 \texttt{int32 -> float32} 与 \texttt{int64 -> float64} 提供受限的 \texttt{VecCnv}，以服务特定循环形态。此外，完整 idiom 覆盖、复杂 reduction 优化及更宽泛的整数向量路径均不包含在此最小路径中。

采用该边界而非直接讨论完整 SIMD 覆盖版，旨在确保研究问题与证据强度相匹配。若主张“LoongArch64 SIMD 后端已完成”，则需解释更多工作负载的中性或负向结果，从而稀释 \texttt{lu.small} 的收益验证。采用最小可用路径，可将收益直接归因于 Loop Vectorization 能否真正转化为 LSX 向量机器码。这里还需要区分两类看似相近、实则不同的优化。标量循环展开改变的是同一执行宽度下的指令排布；最小可用 LSX 路径改变的则是循环体的执行粒度，即将逐标量 lane 的计算转为 128-bit 向量级运算。坚持“最小可用路径”表述，意在强调执行宽度的实际变化，而非标量代码的激进重排。

\begin{lstlisting}[language=C++,caption={最小可用 LSX 路径的保守启用规则（伪代码）},label={lst:lsx-enable-rule}]
if (!is_loongarch64) return ScalarPath;
if (!loop.IsCountable() || !loop.IsUnitStride()) return ScalarPath;
if (packed_type not in {float32, float64}) return ScalarPath;
if (op_set not subset of {ReplicateScalar, Load, Store, Add, Sub, Mul, Cnv}) {
  return ScalarPath;
}
if (!vector_length_matches_128bit_lsx(packed_type)) return ScalarPath;
if (!can_lower_all_required_ir_nodes_to_lsx()) return ScalarPath;
return MinimalLSXPath;
\end{lstlisting}

伪代码~\ref{lst:lsx-enable-rule} 概括了这一方案的启用策略：只有当循环形态、数据类型、向量长度与 lowering 能力同时满足条件时，才进入 LSX 向量路径；否则保持既有标量路径不变。该策略旨在防止未经验证的后端能力干扰正式结论，确保“启用即具备明确语义，失配即退回标量路径”的安全边界。

为使论述落实于代码，下文展示正式方案的实现片段。两段代码分别节选自 \texttt{loop\_optimization.cc} 与 \texttt{code\_generator\_loongarch64.cc}。文中仅省略无关分支并保留原始行号，以建立论述与源码的对应关系。

void HLoopOptimization::GenerateVecMem(HInstruction* org,
                                       HInstruction* opa,
                                       HInstruction* opb,
                                       HInstruction* offset,
                                       DataType::Type type) {
  uint32_t dex_pc = org->GetDexPc();
  HInstruction* vector = nullptr;
  if (synthesis_mode_ == LoopSynthesisMode::kVector) {
    // Vector store or load.
    bool is_string_char_at = false;
    HInstruction* base = org->InputAt(0);
    if (opb != nullptr) {
      vector = new (global_allocator_) HVecStore(
          global_allocator_, base, opa, opb, type, org->GetSideEffects(), vector_length_, dex_pc);
    } else  {
      is_string_char_at = org->AsArrayGet()->IsStringCharAt();
      vector = new (global_allocator_) HVecLoad(global_allocator_,
                                                base,
                                                opa,
                                                type,
                                                org->GetSideEffects(),
                                                vector_length_,
                                                is_string_char_at,
                                                dex_pc);
\end{lstlisting}

代码清单~\ref{lst:vec-ir-generation} 对应了标量循环改写为向量 IR 的步骤。其核心在于区分两类关键向量语义：一是将循环不变量扩展为 \texttt{HVecReplicateScalar}，二是将数组访问重写为 \texttt{HVecLoad/HVecStore}。这对应了伪代码中启用条件达成后的实际 IR 路径。

\begin{lstlisting}[language=C++,numbers=left,firstnumber=6081,basicstyle=\ttfamily\scriptsize,caption={LSX lowering 中的广播入口（节选自 \texttt{code\_generator\_loongarch64.cc}）},label={lst:lsx-lowering-core}]
void LocationsBuilderLOONGARCH64::VisitVecReplicateScalar(HVecReplicateScalar* instruction) {
  LocationSummary* locations = new (GetGraph()->GetAllocator()) LocationSummary(instruction);
  HInstruction* input = instruction->InputAt(0);
  bool is_zero = IsZeroBitPattern(input);
  switch (instruction->GetPackedType()) {
    case DataType::Type::kFloat32:
    case DataType::Type::kFloat64:
      locations->SetInAt(0, is_zero ? Location::ConstantLocation(input)
                                    : Location::RequiresFpuRegister());
      locations->SetOut(is_zero ? Location::RequiresFpuRegister()
                                : Location::SameAsFirstInput());
      break;
    default:
      LOG(FATAL) << "Unsupported SIMD replicate type " << instruction->GetPackedType();
      UNREACHABLE();
  }
}

void InstructionCodeGeneratorLOONGARCH64::VisitVecReplicateScalar(HVecReplicateScalar* instruction) {
  LocationSummary* locations = instruction->GetLocations();
  FRegister dst = locations->Out().AsFpuRegister<FRegister>();
  if (IsZeroBitPattern(instruction->InputAt(0))) {
    EmitVecZero(GetAssembler(), dst);
    return;
  }

  ScratchRegisterScope srs(GetAssembler());
  XRegister tmp = srs.AllocateXRegister();
  switch (instruction->GetPackedType()) {
    case DataType::Type::kInt8: {
      Location src_loc = locations->InAt(0);
      XRegister src = src_loc.IsRegister() ? src_loc.AsRegister<XRegister>() : tmp;
      if (src_loc.IsConstant()) {
        __ LoadConst32(src, src_loc.GetConstant()->AsIntConstant()->GetValue());
      }
      EmitVecReplicateFromGpr(GetAssembler(), DataType::Type::kInt8, dst, src);
      break;
    }
    default:
      break;
  }
\end{lstlisting}

代码清单~\ref{lst:lsx-lowering-core} 演示了向量 IR 如何进入 LoongArch64 LSX lowering。第一，\texttt{LocationsBuilder} 明确约束了输入与输出必须落在向量寄存器语义上；第二，\texttt{InstructionCodeGenerator} 路径直接调用 \texttt{EmitVecZero}、\texttt{EmitVecReplicateFromGpr} 等底层 LSX 发射接口。相应地，\texttt{VisitVecAdd} 等方法亦分别调用对应的 \texttt{EmitVec*} 接口，将前端 \texttt{HVec*} 节点转化为具体的 LSX 指令。

\section{实现边界、正确性回归与保守启用策略}

\subsection{实现边界}

方案三的实现集中于 \texttt{art/compiler/optimizing/} 目录下的三个文件。其中，\texttt{loop\_optimization.cc} 开启了 LoongArch64 受限的浮点向量化入口，并构建了 \texttt{VecLoad/Replicate -> VecCnv} 等最小链路；\texttt{code\_generator\_loongarch64.h} 将 SIMD 图的寄存器宽度约束为 \texttt{16 bytes}，以匹配 128-bit LSX 宽度；\texttt{code\_generator\_loongarch64.cc} 则补齐了关键的 LSX lowering，涵盖广播、向量 load/store、浮点加减乘及受限类型转换。

若按对应版本的提交变更量统计，正文正式方案在这三个核心文件上合计新增 \texttt{350} 行、删除 \texttt{59} 行。主体改动集中在 \texttt{code\_generator\_loongarch64.cc}，其新增 \texttt{333} 行、删除 \texttt{53} 行；\texttt{loop\_optimization.cc} 新增 \texttt{14} 行，头文件只做 \texttt{9} 行约束调整。作为对照，完整 SIMD 候选版在同三文件上新增 \texttt{2311} 行、删除 \texttt{188} 行，其中主体新增量同样主要落在 \texttt{code\_generator\_loongarch64.cc} 与 \texttt{loop\_optimization.cc}。按新增代码量计，正文正式方案约为完整候选版的 \texttt{15.1\%}，这也从实现规模上支持了本文“先证明最小可用路径，再讨论更大覆盖范围”的叙事节奏。

代码规模之外，更关键的是实现边界的清晰度。本文未将完整 SIMD 覆盖、更多 idiom 识别或泛化的整数向量路径纳入正式方案，而是专注于验证规则浮点循环所需的最小 LSX lowering 是否成立。这种受限边界使得第 6 章的结果解释更直接，也便于后文与完整 SIMD 候选版形成对照。

\subsection{正确性回归}

由于方案三直接修改编译器后端，任何轻率的放宽都可能导致错误代码生成。因此，本文在进入 benchmark 前重点回归了与 SIMD 图和 JIT 路径直接相关的测试：\texttt{527-checker-array-access-simd}、\texttt{656-checker-simd-opt}、\texttt{570-checker-osr} 和 \texttt{708-jit-cache-churn}。这些回归测试旨在确认新引入的最小 lowering 在目标图结构上的可编译性、可执行性与正确性，而非证明完整后端已覆盖所有 SIMD 场景。

由于重点在于确立“最小可用路径”，正确性验证亦围绕该链路展开，从而避免将完整 SIMD 候选版的复杂性引入正式证据。

\subsection{保守启用策略}

第 6.2 节的伪代码给出了总体启用规则。“保守启用”要求循环形态、向量长度、类型组合与目标 lowering 均满足条件时，向量路径方可落地；否则退回标量路径。这一策略对于编译器优化尤为重要：第一，新增向量路径不会越界干扰其他未验证模式；第二，所得收益可明确归因于最小 LSX 路径，而非更大范围后端变化的偶发结果。

\section{与完整 SIMD 覆盖候选版的边界比较}

对于多工作负载的整体比较，本文采用几何平均 speedup 作为统一统计量，其定义如式~\ref{eq:geomean-speedup} 所示：
\begin{equation}
    \label{eq:geomean-speedup}
    \operatorname{GM}(S_1,\ldots,S_n)=\left(\prod_{i=1}^{n} S_i\right)^{1/n}
\end{equation}
其中，$S_i$ 表示第 $i$ 个 workload 相对对照版本的 speedup。也就是说，正文与附录中的几何平均比较都建立在单 workload 已先按式~\ref{eq:speedup-throughput}--\ref{eq:relative-gain} 换算成同向 speedup 的前提下。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.88\textwidth]{mybenchmark/loongarch64-lsx-full-simd-ablation-geomean.pdf}
    \caption{最小 SIMD 正式方案与完整覆盖候选版的几何平均比较}
    \label{fig:lsx-full-simd-ablation-geomean}
\end{figure}

为了厘清方案三与“完整 SIMD 后端”的边界，本文引入完整 SIMD 候选消融快照（\texttt{Snapshot-E}）进行对比。该快照比较了三种状态：无 SIMD 对照版本 \texttt{S0}、正文正式方案 \texttt{S1} 与完整覆盖候选版 \texttt{S2}。图~\ref{fig:lsx-full-simd-ablation-geomean} 给出了几何平均视角下的总体结果。

结果表明，如果评价维度是“全部可运行 JIT 工作负载的几何平均”，则当前最优版本仍然是正文采用的 \texttt{S1}：\texttt{S1/S0 = 1.0318x}，而 \texttt{S2/S0 = 1.0252x}，\texttt{S2/S1 = 0.9936x}。这表明完整覆盖版虽然补齐了更多 lowering 和 idiom，但在当前阶段仍存在部分 startup 或非关键工作负载的小幅拖累，尚不足以把整体均值推到 \texttt{S1} 之上。

表~\ref{tab:s2-boundary-groups} 进一步揭示，\texttt{S2} 与 \texttt{S1} 的差异实质上是“收益重分布”，而非单向的性能升降。当观察视角切换到 \texttt{SPEC} startup 时，\texttt{S2} 明显落后于 \texttt{S1}；当观察视角切换到一般 \texttt{SPEC} throughput 时，二者又几乎持平；而在 \texttt{DaCapo} 和关键 SIMD 敏感工作负载上，\texttt{S2} 反而能够继续扩大收益。这意味着完整覆盖版的额外能力确实命中了更多模式，但收益并没有均匀地转化为整体默认配置的优势。

然而，\texttt{S2} 仍具研究价值。在关键 SIMD 敏感工作负载上，\texttt{S2} 进一步优于 \texttt{S1}，证明更宽泛的后端覆盖可放大特定模式的收益。基于此，本文将完整覆盖版定位为“候选增强版”或边界比较对象，旨在展示其潜力，而非将其作为当前的默认方案。

从论文论证角度看，当前证据已经足以支持两个明确判断。第一，\texttt{S1} 仍然是整体几何平均意义下更稳妥的正式方案，因为它在保持 \texttt{lu.small} 大幅收益的同时，对 startup 与非关键工作负载的扰动更小。第二，\texttt{S2} 已经展示出继续扩展 LoongArch64 SIMD 覆盖范围的价值，尤其是在 \texttt{lu.small}、\texttt{h2} 和 \texttt{avrora} 这类真正能命中新模式的工作负载上。相对地，现有归档并不足以把 \texttt{S2} 与 \texttt{S1} 的差异进一步收缩为某一项单独实现成本；更稳妥的写法是把它界定为“关键收益更强，但整体默认边界尚未收敛”的候选增强版。

本章首先证明最小可用路径已成立，随后指明完整覆盖候选版在关键工作负载上的优势及其在整体均值上的局限，借此将“已成立的主结论”与“后续扩展方向”进行严格剥离。关于 \texttt{S0/S1/S2} 的全部数据、关键工作负载结果与解释边界，详见附录第~\ref{app:full-simd-ablation} 节。

在完成方案三自身论证之后，正文最后还需要回答一个更高层的问题：三项正式方案在统一设置下究竟分别解决了什么，以及它们能否被看作同一种“默认优化项”。图~\ref{fig:final-comparison-heatmap} 汇总了正式对比快照（\texttt{Snapshot-A}）中五个代表性工作负载的统一结果。

从图~\ref{fig:final-comparison-heatmap} 可以得到三个直接结论。第一，方案一在 \texttt{pmd} 上最具代表性，说明它更适合解释短生命周期工作负载的 JIT 进入时机问题。第二，方案二在 \texttt{pmd} 与 \texttt{mpegaudio} 上只有弱性能提升，却在 \texttt{lu.small} 上回退，说明它只能被理解为定向微优化。第三，方案三在 \texttt{lu.small} 上取得压倒性收益，但对 \texttt{pmd} 呈中性，对 \texttt{sor.small} 与 \texttt{fft.small} 亦未产生同等提升，表明其作用对象严格限定于规则浮点数值内核，而非泛指所有数值型负载。

三项方案并无高下之分，而是针对不同主路径的分工优化。方案一聚焦控制流与 JIT 进入时机，方案二针对字符串热路径的数据搬移，方案三则填补规则浮点数值内核的后端向量化缺口。抽象而言，三者分别处理阶段边界、固定框架成本与执行宽度这三个层面的问题。基于此，全文将这三者作为面向不同主导瓶颈的独立论证路径，而非同类技术的版本更迭。此外，\texttt{DexFileVerifier} 属于启动期正交案例，故未纳入 \texttt{Snapshot-A} 的统一对比。

此叠加结果进一步明确了研究结论：LoongArch 平台 ART 的性能优化无法依赖简单的策略堆砌，而需围绕具体工作负载的主路径进行独立研判。为此，本文采取“分别分析、分别验证”的组织方式，规避了强行提出统一默认配置的工程误区。

\section{本章小结}

本章论证了全文证据强度最高的结论，即 LoongArch64 最小可用 LSX 浮点 SIMD 路径已经成立，并可在规则浮点数值内核上产生显著、稳定且可解释的性能提升。通过明确问题定义、限定最小能力边界、展示 IR 到 LSX 指令的 lowering 链路、回归正确性约束，并结合 \texttt{Snapshot-A} 与 \texttt{Snapshot-B} 两类证据，本文将方案三从“一个有效方案”提升为“全文主结论”。

进一步地，与完整 SIMD 覆盖候选版的比较表明，当前正式方案 \texttt{S1} 仍是整体几何平均意义下更稳妥的版本，而完整覆盖候选版 \texttt{S2} 更适合作为后续扩展方向保留。再结合与方案一、方案二的统一比较和叠加效应分析，本文得到更系统的结论：LoongArch 平台 ART 的性能优化必须围绕具体工作负载的主导成本展开。核心结论不仅需具备性能提升，还应清晰界定其有效范围、作用机理及其组合局限性。第 7 章将在此基础上对全文结论与后续工作进行总结。
