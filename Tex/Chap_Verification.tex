\chapter{实验设计与正确性验证}\label{chap:verification}

\section{实验平台、实验快照与数据组织}

第 3 章给出了 LoongArch 平台 ART 执行能力构建。第 5 章和第 6 章将依次展开问题筛选与代表性案例分析，以及主结论与综合讨论。
本章位于两者之间，其任务是说明这些后续结论由怎样的实验设计支撑，并回答两个问题：其一，适配后的
执行引擎是否具备可靠的语义正确性；其二，后续性能结果是否建立在一致、可重复的实验条件之上。

围绕上述目标，本文将实验分为正确性验证和性能评测两部分。所有实验统一建立在同一 LoongArch64
目标设备和同一源码状态下，并遵循如下顺序：
\begin{enumerate}
    \item 完整编译当前 ART 产物；
    \item 采用轻量同步方式部署到目标机；
    \item 执行目标机回归与类库验证；
    \item 在验证通过后运行基准测试，采集分数、日志与热点数据。
\end{enumerate}

\subsection{实验环境与执行设置}

本文的实验平台基于真实 LoongArch64 目标设备，处理器为龙芯 3A6000，四核，主频
\texttt{2.5\,GHz}，内存为 \texttt{16\,GB}；目标系统为 Android 15，内核版本为
Linux 6.6.46。软件侧以 AOSP 15 源码中的 \texttt{art/} 子项目为研究对象，在完成第 3 章所述
平台适配后开展后续验证与性能评测\citep{Loongson3A6000DataBook2023,AospArtAndroid15R1}。

本文的正式性能结论统一建立在 LoongArch64 64 位 \texttt{debug} ART 与 \texttt{JIT} 模式下。
选择这一设置有两方面原因。第一，\texttt{debug} 构建更容易暴露调用约定、异常恢复和慢路径跳转等
平台相关错误，有利于在适配尚未完全稳定时完成收敛。第二，第 5 章与第 6 章中的正式方案都在相同设置下
完成对比，因此能够保证前后章节的实验条件一致。

ART 改动统一通过 \texttt{art/tools/buildbot-build.sh --target} 完整编译，之后采用轻量同步方式
将相关产物部署到目标机。保留这一执行链路的目的，在于保证待测产物与当前源码状态一致，而不是将论文
正文写成操作手册式的环境说明。

\section{正确性验证链路：run-test、libcore 与目标机回归}

\subsection{分层验证思路}

本文采用分层验证方式约束正确性，具体包括以下三个层次。
\begin{enumerate}
    \item \textbf{宿主机侧测试。} 用于尽早发现与平台化改动相关的公共组件回归，例如 DEX 处理、
    命令行参数解析和编译器基础设施错误。
    \item \textbf{目标机侧 run-test。} 用于验证解释执行、编译执行、异常处理、对象访问和调用约定等
    执行引擎核心语义。
    \item \textbf{libcore 测试。} 用于进一步验证 Java 核心类库层面的 API 行为是否正常。
\end{enumerate}

这种分层结构的意义在于：宿主机侧测试负责前置过滤，目标机侧 run-test 负责运行时语义验收，
libcore 测试则提供更接近 Java 应用视角的补充证据。前一层通过后，才进入下一层验证与后续性能评测。

\subsection{\texorpdfstring{目标机侧 \texttt{run-test} 整体验收}{目标机侧 run-test 整体验收}}

目标机侧 run-test 是本文验证执行引擎正确性的核心手段。整体验收使用如下命令：
\begin{lstlisting}[language=bash,basicstyle=\ttfamily\small]
art/test.py -r --target --no-prebuild --debug --no-image --64 --all-compiler -j 7
\end{lstlisting}

该命令固定了目标机、\texttt{debug}、\texttt{no-prebuild}、\texttt{no-image} 和 64 位等
关键条件，并通过 \texttt{--all-compiler} 展开 \texttt{interp-ac}、\texttt{interpreter}、
\texttt{jit}、\texttt{jit-on-first-use}、\texttt{optimizing}、\texttt{speed-profile}
和 \texttt{baseline} 七种 compiler 变体。由于 \texttt{art/test} 目录当前包含
\texttt{1033} 个 run-test 用例，因此理论配置总数为 \texttt{7231}。测试框架会依据
\texttt{knownfailures.json} 中的规则自动跳过不适用配置，最终执行结果如
表~\ref{tab:target-run-test-result} 所示。

\subsection{\texorpdfstring{\texttt{libcore} 测试结果}{libcore 测试结果}}

仅依赖 run-test 仍不足以证明 Java 核心类库层面的行为完全正确，因此本文进一步引入 libcore
测试集，用于覆盖集合框架、输入输出、并发、数学运算、加解密与网络等 Java API 语义。按当前实验
归档保留的包级摘要，设备侧已覆盖 libcore 的主要测试包，验证结果以通过为主，少量测试因架构条件
限制被自动跳过。现有记录保留的是包级摘要而非逐包统计明细，因此本文不再将其写成精确通过率数字；
这些自动跳过项不涉及执行引擎核心语义，不影响主要正确性结论。

\subsection{优化阶段的最小相关回归}

性能优化阶段并不重复执行全量系统回归，而是遵循“最小相关回归优先”的原则。即每个候选优化方案在进入
基准测试之前，先根据改动所在模块选择直接受影响的目标机测试集合。本文三项正式方案采用了如下代表性
验证方式：
\begin{itemize}
    \item \textbf{方案一（JIT 分层热度阈值调整）。} 重点验证 \texttt{708-jit-cache-churn}、
    \texttt{667-jit-jni-stub} 等 JIT 相关用例。
    \item \textbf{方案二（运行时字符串搬运批量化）。} 重点验证
    \texttt{624-checker-stringops}、\texttt{729-checker-polymorphic-intrinsic}、
    \texttt{595-profile-saving}、\texttt{570-checker-osr}、
    \texttt{667-jit-jni-stub} 和 \texttt{708-jit-cache-churn}。
    \item \textbf{方案三（LoongArch64 LSX 浮点 SIMD 向量化）。} 重点验证
    \texttt{527-checker-array-access-simd}、\texttt{656-checker-simd-opt}、
    \texttt{570-checker-osr} 以及 \texttt{708-jit-cache-churn}。
\end{itemize}

这种做法的目的，是在保证验证效率的同时维持结论可信度。若相关回归未通过，则基准测试分数不具有
解释价值；只有在最小相关回归通过后，后续性能差异才可以归因于方案本身，而不是功能错误或未定义行为。

\section{正式工作负载选择与数据集组织}

\subsection{基准测试与工作负载选择}

性能评测的目标，不是给出可直接外推到所有 Android 应用场景的绝对结论，而是在统一实验条件下观察
执行引擎优化对代表性工作负载的影响。基于这一目标，本文选择 DaCapo 与 SPECjvm2008 作为主要
基准测试集合\citep{Blackburn2006,SPECjvm2008}。前者更偏向对象分配、字符串处理与复杂控制流；
后者则包含更接近经典 JVM 数值与吞吐路径的工作负载。已有研究也表明，不同基准测试子项在分配速率、
存活集规模和 GC 行为上存在显著差异，因此基准选择本身就是实验设计的一部分
\citep{Lengauer2017GCBench,Prokopec2019Renaissance}。

本文并未从全部可运行 benchmark 中任意抽取 5 个工作负载，而是按照四项原则进行收缩：其一，工作负载应来自
ART/JVM 托管运行时研究中常用的代表性基准集合；其二，五个工作负载合起来必须覆盖本文关心的典型执行模式，
即短生命周期控制流、稳态吞吐热路径和规则浮点数值内核；其三，工作负载必须能够在热点分析与 flamegraph 中
稳定命中主导成本，而不是只对应局部噪声热点；其四，工作负载必须共享统一的验证链、统一的 JIT 模式与正式
对比快照，能够纳入同一组正文主图进行比较。只有同时满足这四项条件的 workload，才进入本文正式图表。

基于上述原则，本文在正式图表中保留的五个工作负载如表~\ref{tab:formal-workload-selection} 所示。

这五个 workload 共同覆盖了本文的三类正式问题：\texttt{pmd} 对应控制流与 JIT 时机，
\texttt{mpegaudio} 对应运行时热路径数据流，\texttt{lu.small}、\texttt{sor.small} 与
\texttt{fft.small} 共同承担 SIMD 主结论、迁移性对照和复杂边界对照。

\texttt{startup.\allowbreak helloworld} 虽然同样具有研究价值，但它服务于启动期 DEX 校验这一正交案例，
不共享三项正式方案的统一对照设置与结果解释链，因此不并入五个正式 workload，而在后文作为独立案例讨论。
其余可运行子项若不能稳定命中本文关心的主导成本，或更适合用于启动噪声、间接访存与分支主导场景的讨论，
亦不进入正文主图。

其中，DaCapo 的评价指标为执行耗时，单位为 \texttt{msec}，数值越小表示性能越好；SPECjvm2008
的评价指标为 \texttt{ops/m}，数值越大表示吞吐越高。本文在后续分析中始终遵循这一指标方向，不将
不同基准测试的分值含义混为一谈。为避免指标方向不一致造成误读，本文统一先换算为同向的
\textit{speedup}，再报告百分比收益。对于吞吐型指标，其定义如式~\ref{eq:speedup-throughput} 所示：
\begin{equation}
    \label{eq:speedup-throughput}
    S_{\text{throughput}} = \frac{M_{\text{scheme}}}{M_{\text{control}}}
\end{equation}
其中，$M_{\text{scheme}}$ 和 $M_{\text{control}}$ 分别表示方案版本与对照版本的吞吐结果。对于时延型指标，
其定义如式~\ref{eq:speedup-latency} 所示：
\begin{equation}
    \label{eq:speedup-latency}
    S_{\text{latency}} = \frac{T_{\text{control}}}{T_{\text{scheme}}}
\end{equation}
其中，$T_{\text{scheme}}$ 和 $T_{\text{control}}$ 分别表示方案版本与对照版本的执行耗时。本文随后统一按
式~\ref{eq:relative-gain} 报告“相对对照版本收益”：
\begin{equation}
    \label{eq:relative-gain}
    G = (S - 1)\times 100\%
\end{equation}
在这一记号下，无论原始指标是 \texttt{msec} 还是 \texttt{ops/m}，只要 $G>0$ 就表示方案版本相对对照版本受益。

在这一命名体系下，正文主结果统一来自正式对比快照（\texttt{Snapshot-A}）；若需要判断收益是否具有
稳定性，则进一步引用统计验证快照（\texttt{Snapshot-B}）。其余快照仅服务于特定章节的机制补充或
边界分析，不参与三项正式方案的统一总比较。

\begin{itemize}
    \item \textbf{正式对比快照（\texttt{Snapshot-A}）。} 该快照用于正文主表和主图，包含统一正式
    对比设置下的对照版本、三项正式方案以及叠加状态。本文随后引用的单次正式结果若无特别说明，均指向
    该快照。其对照版本结果如表~\ref{tab:formal-baseline-values} 所示。
    \item \textbf{统计验证快照（\texttt{Snapshot-B}）。} 该快照仅用于验证两条最关键的性能主张，
    即方案一在 \texttt{pmd} 上的收益方向和方案三在 \texttt{lu.small} 上的稳定收益。其结果单独
    展示，不与 \texttt{Snapshot-A} 的正式对比结果混算。
    \item \textbf{历史对照归档。} 该部分数据仅用于保留较早阶段的对照记录，不再作为三项正式
    方案统一比较的主数据源。
\end{itemize}

本文将 3 轮重复测量作为结论强度判断的最小样本量，其目的不是进行严格的统计显著性检验，而是回答一个更直接
的问题：某条主张在同日、同设备、同模式下究竟表现为“稳定收益”，还是仅表现为“方向上可能受益”。现有
\texttt{Snapshot-B} 已足以把方案一与方案三区分开来：前者具有正收益样本，但波动明显；后者则形成稳定且
显著的重复测量结果。若后续研究需要更强统计保证，则应进一步扩展到更多轮次，并引入配对检验或 bootstrap
等方法。

\subsection{数据采集与分析方法}

为保证性能分析不仅停留在单一分数层面，本文在基准测试运行时同步保留如下原始产物：
\begin{itemize}
    \item \texttt{run.log}：记录脚本调用、远端命令和运行参数；
    \item \texttt{perf.data}：采样得到的原始性能数据；
    \item \texttt{report\_symbol.txt}：符号级热点汇总；
    \item \texttt{report\_callgraph.txt}：调用图视角的热点信息；
    \item \texttt{flamegraph.svg}：火焰图，用于直观展示热点分布。
\end{itemize}

这些数据使后续优化章节可以同时从分数变化、热点分布变化和固定成本变化三个层面解释优化结果，而不是仅凭
单次跑分做出过度推断。正式图表所使用的数据、图文件和作图脚本，也统一保存在外部实验归档目录中，
便于后续交叉核验。

\section{有效性威胁与控制策略}

尽管本文已经通过统一设备、固定编译与部署顺序、最小相关回归和固定数据集组织方式控制实验变量，
面向 JIT 运行时的性能研究仍然不可避免地受到若干因素影响。为使后续优化章节的结论不超出证据范围，
本文对以下因素予以明确约束。

\begin{enumerate}
    \item \textbf{设备状态与后台负载扰动。} 基准测试结果会受到目标机温度、后台服务活动、
    CPU 频率波动和前序运行历史的影响。因此，本文不混用不同轮次的数据源，而是将
    \texttt{Snapshot-A} 与 \texttt{Snapshot-B} 严格分离。
    \item \textbf{基准测试覆盖范围有限。} 本文正文最终保留的正式工作负载包括
    \texttt{pmd}、\texttt{mpegaudio}、\texttt{lu.small}、\texttt{sor.small} 和
    \texttt{fft.small}。这些工作负载已经能够支撑第 5 章和第 6 章的主要结论，但对并发类工作负载、
    复杂服务型应用和更长生命周期应用的覆盖仍然有限。因此，正文结果应被理解为固定实验设置下的
    阶段性结论，而不是 LoongArch 平台 ART 的完整性能画像。
    \item \textbf{\texttt{debug} 构建限制。} 正式性能结论统一建立在 LoongArch64
    \texttt{debug} ART 环境下。这一设置有利于适配阶段的问题暴露，但也会放大部分 JIT 调试信息与
    运行时固定成本。因此，本文所有性能结论都被限制为固定 LoongArch64 \texttt{debug JIT}
    条件下的阶段性结果，不直接外推到 \texttt{release} 构建或其它系统配置。
    \item \textbf{重复测量样本数有限。} 第 5 章和第 6 章仅对最关键的两条性能主张进行了 3 轮重复测量，
    其目的在于区分“可稳定复现的收益”和“仍需进一步验证的收益方向”，而不是进行严格的统计显著性检验。
    因此，论文使用原始散点、均值和标准差表达结论强度，而不滥用显著性术语。
    \item \textbf{JIT 符号可观测性有限。} 部分实验归档中存在 \texttt{perf-*.map} 缺失或
    JIT Java 符号不完整的情况。这意味着火焰图和 \texttt{report\_symbol.txt} 更适合用于判断
    “热点路径是否被命中”和“固定成本是否相对变化”，而不适合支撑过于细粒度的方法级归因。
    \item \textbf{JIT 触发窗口对短生命周期 workload 敏感。} 对 \texttt{pmd} 一类运行时间较短的
    workload 而言，阈值微调可能改变某些热点方法是否来得及进入第一层编译态。即便实验已限定在同机、同日与
    同模式下，少量运行时状态差异仍可能导致编译与否的边界翻转。因此，本文对方案一只写“存在受益方向”而不
    将其升级为稳定均值收益。
\end{enumerate}

综上，本文并不宣称已经完全消除了温度、后台活动、GC 和 JIT 触发时机带来的所有扰动；更准确的说法是，
正文已经通过快照分层和最小相关回归，把这些扰动限制在可解释范围内，并据此区分“单次正式结果”“同日重复测量”
与“仍待进一步加强的主张强度”。

\section{本章小结}

本章从实验目标、验证层次、实验快照体系和有效性威胁控制等方面，给出了本文的实验设计与正确性验证
方法。其核心作用不在于展开作者本地脚本细节，而在于说明第 3 章的适配结果如何得到语义正确性的支撑，
以及后续性能结论为何能够建立在一致、可重复的实验条件之上。基于这一验证框架，第 5 章将在完成问题筛选后展开代表性案例，
第 6 章再集中讨论全文主结论。
